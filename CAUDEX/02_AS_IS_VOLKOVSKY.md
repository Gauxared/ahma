# 02. AS-IS — Волковский ГОК

## 1. Назначение анализа

Волковский ГОК используется как первый реальный reference case СтройИнтел. Цель этого документа — восстановить фактический информационный поток **от плановой работы до денег**, а не пересказать текущий dashboard.

Важно: часть материалов представляет собой аналитические сводки, а не первичку. Поэтому ниже отдельно различаются:

- **первичный/операционный источник** — ОЖР, суточка, КС-2/КС-3, М-15/ОС-15, банк, договор и т.п.;
- **производная модель** — ЦИМ, КСГ, штабной документ, dashboard;
- **экспертное утверждение** — вывод, который ещё требует подтверждения источником.

## 2. Что происходит на объекте сейчас

По штабному статусу на 10.09 физические фронты продолжают двигаться, однако главный кризис находится не в полном останове производства, а в разрыве между выполнением, документальным закрытием и деньгами.

Ключевые симптомы:

- договорный срок 26.08 просрочен;
- готовый физический фронт по хоз-быт КЖ ещё не превращён в подписанный КС-2;
- монтаж давальческого оборудования идёт при незакрытых актах передачи;
- граница земляных работ между сторонами не оформлена;
- отдельные дополнительные/изменённые работы требуют письма и договорного основания;
- касса объекта почти исчерпана, часть нагрузки держит собственник.

Следовательно, управление объектом фактически распадается минимум на четыре взаимосвязанных контура:

1. **производство** — что реально сделано;
2. **исполнительная/доказательства** — чем это подтверждено;
3. **закрытие** — что предъявлено и принято;
4. **денежный контур** — что оплачено и когда.

## 3. AS-IS информационный поток

### 3.1 Плановая база

Плановые работы и объёмы приходят из нескольких источников:

- смета/ВОР;
- КСГ;
- договорные сроки и вехи;
- отдельные технические/проектные документы.

В ЦИМ это уже частично сведено в лист `07·План_Факт`, где существует искусственный код позиции и плановый объём.

Проблема: канонический идентификатор работы ещё не доказан как устойчивый бизнес-ключ между всеми документами. Коды вида `КЖ-Б1`, `ЛОС-Б1`, `НАК-04` удобны для модели, но должны иметь формальное правило образования и связь с исходными позициями.

### 3.2 Получение факта с площадки

Текущий целевой механизм ЦИМ:

`прораб/площадка → суточная форма → код позиции → План_Факт`

Суточная форма хранит:

- дату;
- код;
- описание;
- основание;
- объём;
- единицу;
- место;
- исполнителя/бригаду;
- примечание.

В самой ЦИМ зафиксировано важное правило: **факт вносится приростом за смену, а не нарастающим итогом**, иначе агрегирование через SUMIFS приводит к двойному счёту.

Второй факт-контур — ОЖР. В нём уже видны события производства, но значительная часть записей не содержит количественного объёма. Такие записи дают доказательство вида «работа происходила / фронт начат / операция выполнялась», но не всегда дают достаточное основание для количественного plan/fact.

### 3.3 Нормализация и сопоставление

Сейчас сопоставление факта с плановой работой частично выполняется вручную через код позиции. Для новых работ код должен быть заведен до приёмки факта.

Это создаёт узкое место:

`сырая запись → человек определяет код → ЦИМ может посчитать факт`

Для продукта этот шаг должен превратиться в отдельный matching pipeline:

`raw fact → normalized fact → WorkItem candidate(s) → confidence/rule → confirmed link`

AI может быть полезен только в формировании кандидатов по грязному тексту. Финальная количественная связь должна быть проверяемой.

### 3.4 Расчёт plan/fact

Текущая методика в ЦИМ алгоритмически проста:

- сумма факта по коду;
- остаток `план − факт`;
- доля `факт / план`;
- дата последнего движения.

Это хороший кандидат на полностью детерминированный backend-модуль.

При этом сам файл демонстрирует важный риск качества: в программном чтении части формул присутствуют `#NAME?`, то есть Excel-расчёт и внешний parser/runtime не гарантированно дают одинаковый результат. Поэтому будущий продукт не должен зависеть от того, пересчиталась ли конкретная workbook-формула в клиентском Excel.

### 3.5 Подтверждение выполненного

Физический факт сам по себе не означает готовность к закрытию.

Для разных работ требуются разные evidence:

- ОЖР;
- АОСР;
- исполнительная геодезия;
- ВОР;
- фото;
- акты передачи давальческого;
- паспорт/комплектность оборудования;
- письма по допработам/изменениям.

На Волковском это видно особенно ярко:

- по КЖ физика есть, но ВОР/КС-2 не закрыты;
- по скрытым работам есть долг исполнительной документации;
- монтаж давальческого идёт при проблеме с ОС-15/М-15;
- по земляным работам нельзя брать агрегированный график как объём к закрытию — требуется геодезия/ВОР по отдельным операциям.

То есть между `PERFORMED` и `SUBMITTED` обязательно существует самостоятельный этап `EVIDENCED`.

### 3.6 Предъявление и принятие

В текущих материалах ключевым объектом предъявления является КС-2.

AS-IS выглядит так:

`физический фронт → собрать ВОР/ИД → подготовить КС-2 → передать второй стороне → получить принятие`

Сейчас этот поток не представлен единой машиной состояний. В штабном документе он существует как управленческое поручение: собрать документы и превратить сделанное в деньги.

Для системы важно разделить:

- документ сформирован;
- документ предъявлен;
- документ подписан;
- объём частично принят;
- документ возвращён/оспорен.

### 3.7 Оплата

ЦИМ уже показывает, что денежная реальность объекта значительно сложнее простой формулы «пришёл аванс → оплатили работы».

В текущей модели различаются:

- приток от заказчика/генподрядчика;
- прямые расходы объекта;
- непроектная нагрузка на тот же счёт;
- CAPEX;
- финансирование собственника/ИП;
- подотчёт.

Ключевой вывод для продуктовой модели:

**принятый объём, выручка, прибыль и свободная касса — разные сущности.**

Поэтому `PAID` нельзя выводить из расчётной прибыльности. Нужен платёжный event и правило связи платежа с обязательством/КС.

## 4. Реальная цепочка состояния на примерах Волковского

### Пример A — хоз-быт КЖ

Наблюдаемая логика:

`работы выполнены → доказательства частично есть → ВОР/ИД не закрыты полностью → КС-2 не подписан → денег за фронт нет`

Это главный эталон сценария `performed_not_monetized`.

Система должна показать не просто «жёлтый статус», а:

- какой объём выполнен;
- на какую сумму потенциально может быть предъявлен;
- какие evidence отсутствуют;
- кто владелец blocker;
- сколько времени объём находится в зависшем состоянии.

### Пример B — монтаж давальческого

`оборудование физически получено/монтируется → акты передачи/комплектность не полностью подтверждены → риск ответственности и закрытия`

Это отдельный blocker типа `MISSING_HANDOVER_EVIDENCE`.

### Пример C — земляные работы

`график содержит агрегированные объёмы → фактические операции смешаны → прямое использование объёма даст двойной счёт`

Это blocker качества данных, а не производственный blocker.

Система должна остановить финансовое закрытие при неоднозначной семантике объёма.

### Пример D — дополнительная/изменённая работа

`работа физически выполняется → договорного основания/письма нет → риск невозмещаемой себестоимости`

Нужен отдельный тип `COMMERCIAL_BASIS_MISSING`.

## 5. Существующие ручные роли в AS-IS

Точные должностные регламенты из предоставленных материалов не восстановлены полностью, но фактически видны следующие функции:

- площадка/прораб — фиксирует выполненное;
- принимающий факт/координатор — проверяет полноту и кодирует факт;
- ПТО — формирует/собирает исполнительную и закрывающие документы;
- договорный/руководитель — оформляет изменения, границы ответственности, сроки;
- снабжение/ответственный по давальческому — закрывает передачу и комплектность;
- финансовая функция — собирает БДДС и платёжную реальность;
- руководитель проекта — принимает приоритетные решения.

Для MVP эти функции важнее, чем существующее количество LLM-персон. Сначала моделируются действия и ответственности, затем при необходимости интерфейсные роли.

## 6. Главные проблемы AS-IS

### P1. Факт не всегда количественный

ОЖР часто подтверждает событие, но не объём. Нельзя автоматически подставлять приблизительный процент выполнения.

### P2. Нет единого устойчивого ключа работы

Коды ЦИМ полезны, но пока выглядят как локальная система кодирования. Нужна формальная идентичность между сметой, КСГ, суточкой, ОЖР и закрытием.

### P3. `выполнено` смешивается с `закрыто`

Это уже признано в материалах, но пока не стало общей моделью данных.

### P4. Evidence существует как документы, а не как формализованные требования перехода

Не определена единая матрица `work type → required evidence → condition`.

### P5. Dashboard частично является вручную подготовленной витриной

HTML-дашборд содержит статический объект данных и текстовые экспертные выводы. Это полезный прототип интерфейса, но не источник истины продукта.

### P6. Расчёты живут и в Excel, и в коде

Это создаёт несколько мест истины. Формулы первого продуктового контура следует переносить в backend calculation layer с trace.

### P7. Кассовая модель имеет несколько контуров

Прямое сопоставление «объект прибыльный → деньги есть» недопустимо.

### P8. Допработы могут выполняться раньше коммерческого оформления

Это создаёт отдельный тип финансового риска, который должен ловиться до КС-2.

## 7. Точки ручного труда, которые имеет смысл автоматизировать первыми

1. Сопоставление факта из ОЖР/суточки с `WorkItem`.
2. Проверка completeness записи факта.
3. Автоматический количественный plan/fact.
4. Матрица evidence и readiness к предъявлению.
5. Реестр выполненных, но неготовых к КС-2 объёмов.
6. Реестр предъявленных, но не принятых объёмов.
7. Реестр принятых, но не оплаченных обязательств.
8. Автоматическое вычисление возраста каждого blocker.
9. Формирование ежедневного exception list вместо ручного штабного narrative.

## 8. Что пока нельзя считать установленным фактом

Следующие вопросы требуют отдельного discovery/первички и не должны быть «дорисованы» системой:

- полный обязательный набор evidence по каждому типу строительной работы;
- точное юридическое состояние каждого КС-2/КС-3;
- правило связи банковского платежа с конкретным закрытым объёмом;
- универсальный канонический код работы;
- допустимые варианты частичного подписания;
- нормативный SLA для переходов между стадиями;
- состав ролей и права подтверждения в production;
- способ разрешения конфликтов между ОЖР, геодезией, ВОР и сметой.

Эти пункты переходят в следующий этап анализа и должны быть подтверждены не AI-выводом, а бизнес-правилом/источником.

## 9. AS-IS в одной схеме

```text
Смета / ВОР / КСГ
        │
        ▼
   Плановая работа
        │
        │ площадка выполняет
        ▼
Суточка / ОЖР / КС-6а
        │
        │ ручное/полуручное кодирование
        ▼
     План/Факт
        │
        ├──── нет объёма / неоднозначный код ───► ручной разбор
        │
        ▼
Исполнительная документация
АОСР / геодезия / ВОР / фото / акты передачи
        │
        ├──── неполный комплект ───────────────► blocker
        │
        ▼
       КС-2
        │
        ├──── не подписано ────────────────────► blocker
        ▼
       КС-3 / принятие
        │
        ├──── не оплачено ─────────────────────► blocker
        ▼
      Платёж
```

Главный будущий объект СтройИнтел — **не документ и не агент, а переход WorkItem/объёма между этими стадиями**.
