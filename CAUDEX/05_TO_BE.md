# 05. TO-BE — целевой процесс первого контура СтройИнтел

## 1. Цель TO-BE

Первый контур СтройИнтел должен превратить разрозненные документы и записи объекта в доказуемую сквозную историю по каждой работе:

`что запланировано → что выполнено → чем подтверждено → что предъявлено → что принято → что оплачено`.

Целевая система не должна имитировать организационную структуру компании набором LLM-ролей. Она должна хранить единые факты, вычислять состояния и выдавать каждому пользователю нужное представление.

---

## 2. Ключевой результат для пользователя

На любой момент времени руководитель проекта или ПТО должен получить список вида:

| Работа | Выполнено | Подтверждено | Предъявлено | Принято | Оплачено | Blocker | Возраст | Потенциальный эффект |
|---|---:|---:|---:|---:|---:|---|---:|---:|
| `WorkItem A` | 80 м³ | 60 м³ | 40 м³ | 40 м³ | 20 м³ | не хватает АОСР на 20 м³ | 5 дн | X ₽ |

Каждая цифра и blocker должны раскрываться до источника.

Если число вычислить нельзя, система показывает `UNKNOWN`/`MISSING_SOURCE`, а не ноль и не экспертную догадку.

---

## 3. Целевой сквозной процесс

```text
1. ЗАГРУЗКА / ПОЛУЧЕНИЕ ИСТОЧНИКОВ
   │
   ├─ смета / ВОР
   ├─ КСГ
   ├─ суточка
   ├─ ОЖР
   ├─ исполнительная документация
   ├─ КС-2 / КС-3
   ├─ договор / допсоглашения / письма
   └─ банк / БДДС / платёжные документы
   │
   ▼
2. INTAKE + CLASSIFICATION
   │
   ▼
3. EXTRACTION
   │
   ├─ deterministic parser
   ├─ rule/fuzzy matching
   └─ AI fallback только для неоднозначного входа
   │
   ▼
4. NORMALIZATION
   │
   ▼
5. CANONICAL DATA
   │
   ├─ WorkItem
   ├─ ProgressEvent
   ├─ Evidence
   ├─ SubmissionEvent
   ├─ AcceptanceEvent
   ├─ PaymentEvent
   └─ CommercialBasis / Dependency
   │
   ▼
6. DETERMINISTIC ENGINES
   │
   ├─ plan/fact
   ├─ evidence readiness
   ├─ workflow state
   ├─ blockers
   ├─ age / SLA
   ├─ monetary exposure
   └─ later: scheduling / cash / EVM
   │
   ▼
7. BUSINESS FINDINGS
   │
   ▼
8. API / UI / EXPORT / OPTIONAL AI EXPLANATION
```

---

## 4. Этап 1 — Intake

### Цель

Не «понять весь объект», а зарегистрировать каждый входной артефакт и его provenance.

### Для каждого SourceDocument сохраняется

- идентификатор объекта;
- тип документа;
- имя/версия;
- дата документа;
- дата получения;
- источник/контрагент;
- checksum/version;
- статус разбора;
- причина отказа разбора, если есть.

### Инвариант

Ни один файл не исчезает молча.

Исход:

- parsed;
- partially_parsed;
- unsupported;
- failed с указанной причиной.

---

## 5. Этап 2 — Extraction и normalization

СтройИнтел извлекает не «заключение эксперта», а конкретные кандидаты фактов.

Пример записи ОЖР:

```text
10.09 — бетонирование фундамента ФМ2.2, захватка 3 ...
```

После extraction:

```json
{
  "event_date": "2026-09-10",
  "operation": "бетонирование фундамента",
  "location": "ФМ2.2 / захватка 3",
  "quantity": null,
  "unit": null,
  "source_ref": "...",
  "confidence": 0.94
}
```

Если quantity отсутствует в источнике, она остаётся `null`.

---

## 6. Этап 3 — WorkItem matching

Каждый производственный/закрывающий факт должен связываться с канонической работой.

Pipeline:

```text
explicit source code
    ↓ нет
exact normalized match
    ↓ нет
mapping rules
    ↓ нет
fuzzy candidates
    ↓ нет/неуверенно
LLM candidate generation
    ↓
confidence gate
    ├─ auto-confirm по доказанному безопасному порогу
    └─ manual review
```

Система хранит способ сопоставления и историю подтверждения.

### Важно

`WorkItem matching` и `quantity validation` — разные проверки. Можно правильно определить работу, но иметь непригодный объём.

---

## 7. Этап 4 — Расчёт физического факта

`ProgressEvent` является событием прироста, а не нарастающим итогом.

Для количественного plan/fact событие обязательно содержит:

- `work_item_id`;
- `event_date`;
- `quantity`;
- `unit`;
- `quantity_semantics`;
- provenance;
- validation status.

Расчёт:

- `performed_quantity = Σ valid ProgressEvent.quantity`;
- `remaining = planned_quantity - performed_quantity`;
- `progress_ratio = performed_quantity / planned_quantity` при совместимых единицах.

Если измерения несовместимы или семантика неоднозначна, показатель не вычисляется.

---

## 8. Этап 5 — Evidence readiness

Для типа работы хранится профиль обязательных доказательств.

Пример концептуально:

```text
Монолитный бетон
  required:
    - OJR_RECORD
    - AOSR
    - EXECUTIVE_SCHEME when applicable
    - LAB/QUALITY_EVIDENCE when applicable
```

Для каждого выполненного объёма система определяет:

- какие evidence существуют;
- какой объём ими покрыт;
- чего не хватает;
- является ли отсутствие blocker для предъявления.

Результат:

`performed_quantity` и `evidenced_quantity` существуют отдельно.

---

## 9. Этап 6 — Commercial readiness

До предъявления система проверяет не только техдоказательства, но и коммерческое основание.

Возможные основания:

- исходный договорный scope;
- утверждённая смета;
- дополнительное соглашение;
- согласованное изменение;
- письмо/распоряжение с установленным в организации статусом допустимости.

Работа без подтверждённого основания получает blocker, даже если физически выполнена.

---

## 10. Этап 7 — Submission

Предъявление — отдельная business transaction.

Система не должна выводить `SUBMITTED` из наличия файла с названием `КС-2`.

Фиксируются:

- документ;
- дата формирования;
- дата отправки/предъявления;
- контрагент;
- включённые `WorkItem` и объёмы;
- сумма;
- версия;
- статус.

Возможные статусы:

`DRAFT → SUBMITTED → PARTIALLY_ACCEPTED / ACCEPTED / REJECTED / RETURNED_FOR_REVISION`.

---

## 11. Этап 8 — Acceptance

Принятие формируется отдельным событием с доказательством.

Система должна поддерживать частичную приёмку.

Поэтому одна работа может одновременно иметь:

- 100 единиц выполнено;
- 80 подтверждено;
- 60 предъявлено;
- 45 принято.

Один общий цвет для всей строки недостаточен.

---

## 12. Этап 9 — Payment

Оплата подтверждается платёжным событием.

Целевая логика:

```text
accepted amount
   ↓
payment obligation
   ↓
expected due date
   ↓
payment event(s)
   ↓
paid / outstanding / overdue
```

Связь платежа с КС/обязательством может быть:

- точной;
- распределённой;
- частичной;
- неразрешённой.

Неразрешённый банковский платёж не должен автоматически распределяться моделью без правил/подтверждения.

---

## 13. Blocker engine

Blocker — первая полноценная управленческая сущность продукта.

Примеры типов:

- `WORK_ITEM_UNMATCHED`;
- `QUANTITY_MISSING`;
- `QUANTITY_UNIT_MISMATCH`;
- `AMBIGUOUS_QUANTITY_SEMANTICS`;
- `EVIDENCE_MISSING`;
- `HANDOVER_EVIDENCE_MISSING`;
- `COMMERCIAL_BASIS_MISSING`;
- `SUBMISSION_NOT_CREATED`;
- `SUBMISSION_RETURNED`;
- `ACCEPTANCE_PENDING`;
- `PAYMENT_OVERDUE`.

Каждый blocker содержит:

- affected entity/work item;
- transition, который он блокирует;
- opened_at;
- owner/responsibility if known;
- required action;
- source/evidence;
- severity;
- monetary exposure if computable;
- resolved_at.

### Главное правило

Blocker выводится из отсутствующего/конфликтующего факта детерминированно. LLM может только сформулировать его объяснение пользователю.

---

## 14. Приоритизация «что делать сегодня»

MVP может строить очередь действий без AI ranking.

Первый прозрачный score допускается как конфигурационная формула, например по факторам:

- денежный эффект;
- возраст blocker;
- близость договорного срока;
- criticality transition;
- наличие ответственного;
- возможность закрыть blocker текущим действием.

Формула должна быть версионируемой и объяснимой.

До доказательства такой формулы допустим простой deterministic sort, а не «агент сам решит приоритет».

---

## 15. Пользовательские представления

Один backend — несколько views.

### Руководитель проекта

- сумма выполненного, но не предъявленного;
- сумма предъявленного, но не принятого;
- сумма принятого, но не оплаченного;
- top blockers;
- просроченные переходы;
- ближайшие действия.

### ПТО

- работы с missing evidence;
- документы к подготовке/подписанию;
- coverage evidence по объёмам;
- returned submissions.

### Финансы/руководитель

- accepted but unpaid;
- due/overdue;
- прогноз притока по подтверждённым обязательствам;
- отдельно: project cash-flow.

Ни одно view не требует отдельного LLM-агента.

---

## 16. Место КСГ и сроков

Календарная аналитика подключается после стабилизации `WorkItem` и факта.

КСГ связывается с теми же `WorkItem`/work packages и даёт:

- planned dates;
- dependencies;
- milestones;
- float;
- critical path.

После этого blocker физического/документального перехода может быть связан с временным влиянием.

До появления корректной сети система не должна генерировать фиктивный critical path текстом LLM.

---

## 17. Место EVM

EVM — производный слой, а не входной feature.

Он разрешается только после однозначного определения:

- `PV` из baseline/calendar + budgeted work;
- `EV` из принятой организацией методики earned progress;
- `AC` из фактических затрат.

Если один из входных контуров неполон, показатель маркируется как `NOT_COMPUTABLE` с причиной.

---

## 18. Human-in-the-loop

Человек участвует там, где система не может доказать безопасное решение.

Human review требуется, например, при:

- неоднозначном WorkItem match;
- конфликте единиц;
- неизвестной семантике количества;
- неразрешённом распределении платежа;
- спорном commercial basis;
- новом шаблоне документа, который parser не поддерживает.

Но человек не должен вручную пересчитывать формулы или собирать каждый dashboard.

---

## 19. Минимальный release flow

Первый release не обязан покрывать весь document universe.

Достаточный vertical slice:

```text
Смета/ВОР
   +
Суточка/ОЖР
   +
Evidence registry
   +
КС-2
   +
Payment import
   ↓
WorkItem lifecycle
   ↓
performed_not_monetized registry
   ↓
blockers + provenance
```

Это должно работать end-to-end на Волковском и затем на втором объекте.

---

## 20. Definition of Done TO-BE MVP

TO-BE считается реализованным, если пользователь может открыть объект и без ручной аналитической сборки получить ответ:

> «На X ₽ есть подтверждённое физическое выполнение, которое ещё не стало оплаченной выручкой. Вот конкретные работы, текущий этап каждой, blocker, владелец, возраст и документы-источники.»

Система должна позволять провалиться от агрегата до source fragment.

Если такой ответ зависит от свободного рассуждения LLM — TO-BE не выполнен.
