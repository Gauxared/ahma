# 08. MVP Requirements — СтройИнтел

## 1. Цель MVP

MVP СтройИнтел должен не «анализировать стройку вообще», а доказуемо решать один сквозной сценарий:

> найти выполненные работы, которые не дошли до предъявления/принятия/оплаты, показать причину остановки и источник каждого вывода.

Первый reference case — Волковский ГОК.

---

## 2. Основной пользовательский результат

Для каждой существенной работы пользователь должен видеть:

- плановый объём;
- фактический выполненный объём;
- подтверждающие evidence;
- текущую стадию жизненного цикла;
- следующий ожидаемый переход;
- blocker;
- возраст blocker;
- денежный эффект зависшего объёма, если он вычислим;
- ссылки на первичные источники.

---

## 3. Functional requirements

### FR-01. Импорт источников

Система должна принимать как минимум:

- смету/ВОР;
- суточную форму;
- ОЖР;
- КС-2;
- КС-3;
- банковский/платёжный источник;
- КСГ/график;
- договор/допсоглашение/письмо как коммерческое основание.

Допустимые форматы первого MVP определяются реализованными parser profiles; неподдерживаемый формат должен завершаться явным `UNSUPPORTED_PROFILE`, а не частичным тихим разбором.

### FR-02. Версионирование источников

Каждый импорт должен иметь `documentId`, checksum и версию/дату получения. Повторная загрузка изменённого документа не должна незаметно переписывать происхождение ранее рассчитанных facts.

### FR-03. Канонический WorkItem

Система должна иметь единую сущность `WorkItem`, независимую от строки конкретного документа.

Связи сметы, суточки, ОЖР, КСГ и КС-2 с работой должны храниться отдельно и быть трассируемыми.

### FR-04. Регистрация ProgressEvent

Количественный факт выполнения должен сохраняться событием с:

- датой;
- количеством;
- единицей;
- WorkItem;
- SourceRef;
- способом сопоставления.

### FR-05. Защита от двойного счёта

Система должна отклонять или маркировать как конфликт:

- повторную загрузку одного факта;
- смешение накопительного и инкрементального количества;
- несовместимые единицы;
- агрегированные объёмы, которые нельзя безопасно разложить по операциям.

### FR-06. Matching pipeline

Порядок сопоставления факта с WorkItem:

`exact code → alias/rule → fuzzy → AI candidate → manual review`.

AI не может автоматически подтвердить match при недостаточном confidence или конфликте нескольких кандидатов.

### FR-07. Evidence registry

Система должна хранить evidence отдельно от ProgressEvent и уметь связывать одно evidence с одной или несколькими работами/объёмами.

### FR-08. Readiness rules

Для типа работы должна настраиваться матрица обязательных evidence.

Пример результата:

```text
READY_FOR_SUBMISSION
MISSING_AOSR
MISSING_GEODESY
MISSING_HANDOVER_ACT
COMMERCIAL_BASIS_MISSING
```

### FR-09. State chain

Система должна вычислять состояние объёма по цепочке:

`PLANNED → PERFORMED → EVIDENCED → SUBMITTED → ACCEPTED → PAID`.

Состояния рассчитываются по событиям, а не редактируются произвольно пользователем.

### FR-10. Частичные объёмы

Разные части одной работы могут находиться на разных стадиях. MVP не должен сводить WorkItem к единственному глобальному статусу.

### FR-11. КС-2

Для КС-2 необходимо различать минимум:

- draft;
- submitted;
- accepted;
- rejected;
- partial.

Должна существовать связь строк КС-2 с WorkItem.

### FR-12. Оплата

`PAID` возникает только из PaymentEvent/подтверждённой связи с платёжным обязательством.

Факт прихода денег на общий счёт не должен автоматически означать оплату конкретного WorkItem.

### FR-13. Blockers

Система должна автоматически создавать blockers для выявленных разрывов, включая минимум:

- unresolved matching;
- unknown quantity;
- missing evidence;
- missing commercial basis;
- KS-2 not prepared/submitted/accepted;
- payment not linked;
- source conflict;
- double-count risk.

### FR-14. Возраст blocker

Для blocker должна рассчитываться длительность открытого состояния на текущую дату или дату среза.

### FR-15. Monetary impact

Если доступны однозначные цена/стоимость и объём, система должна рассчитывать потенциальную стоимость зависшего объёма.

Если цена отсутствует или спорна, вывод должен быть `UNKNOWN`, а не 0.

### FR-16. Findings

Система должна формировать структурированный finding, содержащий:

```text
subject
condition
severity
computed values
source refs
blocker
next required transition
```

### FR-17. Traceability UI

Из каждого ключевого показателя/вывода пользователь должен иметь возможность перейти к источнику: документ, лист/страница, строка/фрагмент.

### FR-18. Exception-first view

Основной рабочий экран MVP должен приоритизировать отклонения и blockers, а не перечислять все данные объекта одинаковым весом.

### FR-19. AI explanation

LLM может объяснять существующий finding простым языком, но ответ должен строиться только на переданных структурированных facts/findings/source refs.

### FR-20. Unknown-safe behavior

Отсутствующие, неподтверждённые и конфликтующие данные должны сохранять соответствующий статус и не участвовать в расчётах как нули.

---

## 4. Non-functional requirements

### NFR-01. Reproducibility

При одинаковом наборе подтверждённых canonical facts детерминированные показатели и blockers должны воспроизводиться независимо от выбранной LLM.

### NFR-02. Auditability

Любой финансовый/статусный вывод должен восстанавливаться до исходного SourceRef и версии документа.

### NFR-03. Idempotency

Повторный импорт одного и того же источника не должен удваивать события.

### NFR-04. Fail explicit

Ошибки parser/matching/calculation не должны приводить к тихому пропуску строки.

### NFR-05. Separation of concerns

Парсер не рассчитывает бизнес-статус; LLM не рассчитывает деньги; UI не содержит независимую бизнес-логику.

### NFR-06. Configurability

Пороги, обязательные evidence и document profiles должны храниться в конфигурации с effective dates/версиями там, где это применимо.

### NFR-07. Testability

Каждое правило состояния и blocker должно иметь unit/reference-case тест.

### NFR-08. Explainable automation

Автоматический match или статус должен содержать код применённого правила/метода.

---

## 5. UI scope MVP

Минимально достаточно трёх представлений:

### 5.1 Work pipeline

Таблица/реестр работ с колонками:

- WorkItem;
- plan;
- performed;
- evidenced;
- submitted;
- accepted;
- paid;
- blocker;
- blocker age;
- monetary impact.

### 5.2 Blocker queue

Список исключений с фильтрацией по severity/type/owner/age.

### 5.3 WorkItem detail

Карточка одной работы:

- timeline событий;
- evidence;
- submission/acceptance/payment links;
- conflicts;
- sources;
- explanation.

Новые аналитические dashboard-блоки вне этих сценариев не входят в MVP.

---

## 6. AI scope MVP

Разрешены только три класса AI-use-case:

1. извлечение структуры из слабоструктурированного входа;
2. semantic candidate matching;
3. человекочитаемое объяснение structured finding.

Не входят:

- multi-agent debate;
- отдельные цифровые должности ради имитации оргструктуры;
- свободный финансовый анализ;
- автономное принятие решения о готовности/оплате;
- генерация недостающих фактов.

---

## 7. Out of scope

До доказательства первого контура исключаются:

- полноценный EVM как основной продуктовый экран;
- универсальное планирование всех ресурсов объекта;
- predictive ML по срокам/стоимости без корпуса;
- автоматическая генерация полного пакета управленческих документов;
- CRM/ERP-функции общего назначения;
- расширение crew-agents;
- мобильная платформа с отдельной продуктовой логикой;
- автоматическое изменение первичных документов.

---

## 8. MVP metrics

Первый контур оценивается не числом AI-вызовов, а бизнес- и data-quality метриками:

- доля факта, однозначно сопоставленного с WorkItem;
- доля monetary value с полным provenance;
- доля выполненного объёма с подтверждённым evidence;
- сумма/объём `performed_not_submitted`;
- сумма/объём `accepted_not_paid`;
- медианный возраст blockers;
- доля AI matches, потребовавших ручной коррекции;
- false-positive rate критичных findings;
- число silent skips = 0.

---

## 9. Definition of Done MVP

MVP считается состоявшимся, если на Волковском для согласованной существенной выборки работ система без ручной аналитической сборки после импорта способна:

1. построить цепочку план → факт → evidence → КС-2 → принятие → оплата;
2. явно показать недостающие звенья;
3. не придумывать отсутствующие объёмы/цены/документы;
4. показать источник каждого критичного значения;
5. воспроизводимо рассчитать blockers и monetary impact;
6. пережить повторный импорт без двойного счёта;
7. затем пройти тот же сценарий минимум на одном втором объекте без объектных условий в коде.
