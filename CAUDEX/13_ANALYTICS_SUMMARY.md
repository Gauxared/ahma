# 13. Analytics Summary — СтройИнтел

## 1. Коротко: что меняется

СтройИнтел уже не выглядит как «пустой AI-прототип». В проекте есть сильная инженерная база: разбор строительных документов, детерминированные расчёты, provenance, canonical matching, тесты, конфигурация, runtime и production-инфраструктура.

Проблема проекта не в отсутствии функций. Проблема — в **центре тяжести продукта**.

Текущая история во многом строится вокруг:

`объект → выбрать режим/агентов → дать агентам документы → собрать экспертные выводы и пакет отчётов`.

Первый продуктовый контур предлагается перестроить вокруг реального бизнес-процесса:

`работа запланирована → выполнена → подтверждена → предъявлена → принята → оплачена`.

Основной вопрос пользователя:

> Что физически уже сделано, что из этого можно доказать первичкой, что ещё не дошло до КС-2/принятия/оплаты и почему?

---

## 2. Почему нужен продуктовый поворот

Существующая система охватывает слишком много смыслов одновременно:

- проверка смет;
- договорный аудит;
- закупки;
- графики;
- финансовая модель;
- исполнительная документация;
- набор LLM-ролей;
- несколько orchestration-режимов;
- экспорт управленческих документов.

Каждая возможность сама по себе может быть полезной, но вместе они создают риск, что проект становится **технически сложной системой без одного измеримого пользовательского результата**.

По материалам reference case Волковского более явная проблема другая: физическое выполнение, документальное подтверждение и деньги движутся разными контурами. Работа может быть сделана, но не оформлена, не предъявлена, не принята или не оплачена. Именно этот разрыв предлагается сделать первым продуктовым предметом.

---

## 3. Новый продуктовый тезис

Первый СтройИнтел — это не «AI, который анализирует стройку».

Первый СтройИнтел — это:

> **система контроля выполнения и монетизации строительных работ с доказуемой трассировкой до первичных источников.**

Для каждой работы система должна показать:

- план;
- факт;
- подтверждающие документы;
- готовность к предъявлению;
- предъявленный объём;
- принятый объём;
- оплату;
- blocker следующего перехода;
- возраст blocker;
- денежный эффект, если его можно вычислить;
- источник каждого существенного числа и статуса.

Если данных недостаточно — система должна сказать, чего не хватает.

---

## 4. Что происходит с AI

AI не убирается из продукта.

Меняется его роль.

### Было

AI часто выступает как носитель предметной экспертизы и orchestration-центр: разные роли читают объект, рассуждают, передают работу друг другу и формируют выводы.

### Становится

AI работает в тех местах, где вход действительно неоднозначен:

1. извлекает структуру из слабоструктурированных документов;
2. помогает сопоставлять разные названия одной работы;
3. объясняет пользователю уже рассчитанный системой finding.

Внутри системы — normalized data + deterministic rules.

Формула:

`parser → normalization → exact/rules → fuzzy → AI fallback → review`.

AI не должен самостоятельно определять деньги, процент выполнения, оплату, статус КС-2 или существование blocker.

---

## 5. Почему это не «откат назад от AI»

Наоборот, такая граница делает AI полезнее.

LLM наиболее ценна там, где обычный код объективно слаб:

- разный человеческий язык в ОЖР и смете;
- нестандартный текст документа;
- неоднозначное описание места/операции;
- semantic matching;
- объяснение сложного результата пользователю.

Она хуже подходит для задач, где ответ должен быть воспроизводимым и аудируемым:

- арифметика;
- money state;
- количественный plan/fact;
- lifecycle transition;
- SLA/возраст;
- EVM;
- расчёт кассовых показателей.

Для этих задач код не является «менее умным решением» — это правильная технология.

---

## 6. Что сохраняем из текущего проекта

Продуктовый поворот **не означает rewrite**.

Сохраняем и переиспользуем:

- детерминированные `modules/calculations/`;
- formula registry;
- provenance/source trace;
- принцип `UNKNOWN != 0`;
- `modules/documents/`;
- `platform/storage/`;
- существующий canonical matching;
- contracts/primitives;
- ports/adapters;
- PostgreSQL/runtime/jobs/security infrastructure;
- eval/reference-case подход;
- LLM runtime как сервис для разрешённых AI-use-cases.

То есть значительная часть сложной технической работы остаётся полезной.

---

## 7. Что перестаём развивать как центр продукта

До доказательства первого vertical slice замораживаются:

- новые LLM-роли;
- новые «цифровые должности»;
- расширение crew/оркестрации;
- новые режимы маршрутизации к агентам;
- dashboard-визуализации без нового canonical fact;
- свободный финансовый анализ моделью;
- попытка одновременно автоматизировать весь lifecycle строительного объекта.

Старые возможности не требуется немедленно удалять. Они переходят в режим compatibility / experiment / selective reuse.

---

## 8. Основная предметная модель

Центральная единица — `WorkItem`.

Это не строка Excel, не запись ОЖР и не строка КС-2.

Разные источники связываются с одной работой через события и aliases:

```text
Project
 └─ WorkItem
     ├─ ProgressEvent
     ├─ Evidence
     ├─ CommercialBasis
     ├─ SubmissionLine / Submission
     ├─ AcceptanceEvent
     ├─ PaymentObligation / PaymentEvent
     ├─ Blocker
     └─ Finding
```

Это позволяет не смешивать физическое выполнение, документальное подтверждение и денежный контур.

---

## 9. Главное продуктово-техническое правило

**Статус работы нельзя хранить как одно редактируемое поле.**

У работы могут одновременно быть разные объёмы на разных стадиях:

```text
100 м³ planned
80 м³ performed
60 м³ evidenced
50 м³ submitted
45 м³ accepted
20 м³ paid-equivalent
```

Именно разница между этими слоями создаёт полезные пользователю findings.

Например:

- `PERFORMED_NOT_EVIDENCED`;
- `EVIDENCED_NOT_SUBMITTED`;
- `SUBMITTED_NOT_ACCEPTED`;
- `ACCEPTED_NOT_PAID`.

## 10. Первый MVP

MVP не должен «понимать весь объект».

Он должен доказать один сквозной сценарий:

> найти выполненные работы, которые не дошли до предъявления/принятия/оплаты, и объяснить конкретную причину остановки.

Минимальные пользовательские представления:

### Work Pipeline

Одна таблица с:

`plan / performed / evidenced / submitted / accepted / paid / blocker / age / ₽`.

### Blocker Queue

Что требует действий сегодня.

### WorkItem Detail

История одной работы с источниками и переходами.

Всё остальное — после доказательства этого контура.

---

## 11. Какие проблемы MVP должен ловить

Reference cases уже фиксируют ключевые ситуации:

- работа выполнена, но не предъявлена;
- факт есть, но исполнительной документации недостаточно;
- ОЖР описывает событие, но не содержит объёма;
- неоднозначное сопоставление работ;
- повторный импорт;
- накопительный факт ошибочно принят за суточный;
- несовместимые единицы;
- риск двойного счёта земмасс;
- допработа без коммерческого основания;
- давальческое оборудование без документов передачи;
- КС-2 draft не равен предъявлению;
- частичное принятие;
- принято, но не оплачено;
- общий банковский приход нельзя связать с конкретной работой;
- цена неизвестна;
- источники конфликтуют.

Смысл набора — проверять не красоту ответа, а бизнес-корректность и опасные false positives.

---

## 12. Метрики успеха

Проект больше не следует оценивать числом AI-вызовов, количеством ролей или размером отчёта.

Метрики первого контура:

- доля факта, автоматически и однозначно сопоставленного с WorkItem;
- доля значимых чисел с provenance;
- доля выполненного объёма с достаточным evidence;
- объём/сумма `performed_not_submitted`;
- объём/сумма `accepted_not_paid`;
- медианный возраст blockers;
- false-positive rate critical findings;
- доля AI matches, исправленных человеком;
- silent skips = 0;
- повторный import не меняет result.

Главная бизнес-метрика после пилота может быть сформулирована как сокращение времени между физическим выполнением и превращением работы в подтверждённое денежное требование/оплату.

---

## 13. Почему EVM и predictive ML не являются первым шагом

EVM сам по себе не исправляет плохой факт.

До появления надёжных:

- baseline/PV;
- earned progress/EV;
- actual costs/AC

SPI/CPI/EAC будут только красивым производным показателем от спорных данных.

Predictive ML тем более требует накопленной истории и labels.

Поэтому последовательность следующая:

`reliable facts → lifecycle → blockers → schedule/cash → EVM → prediction`.

Не наоборот.

---

## 14. Как выглядит целевая архитектура одной строкой

### Сейчас

```text
Документы → режим → агенты/роли → рассуждение → отчёты
```

### Первый целевой contour

```text
Документы
 → parsers
 → canonical facts
 → deterministic lifecycle/blockers
 → UI/API
 → optional AI explanation
```

Это не отказ от существующей архитектуры ports/adapters. Это смена предметного ядра поверх неё.

---

## 15. Что должен делать разработчик / Codex

Следующий шаг — не придумывать новую систему.

Codex сначала должен провести **read-only technical audit**:

- проверить assumptions `10_CURRENT_CODE_MAPPING.md`;
- найти конкретные reuse points;
- отметить зависимости legacy agent flow;
- предложить минимальный module boundary нового contour;
- сверить contracts/persistence gaps;
- проверить, какие acceptance cases можно построить на существующих fixtures.

Только после этого начинается реализация `11_DELIVERY_BACKLOG.md`.

---

## 16. Критерий, что поворот оказался успешным

На Волковском система должна пройти путь:

```text
source
 → canonical work
 → fact
 → evidence
 → submission
 → acceptance
 → payment
 → blocker/finding
```

и показать источник каждого перехода.

Затем тот же механизм должен пройти второй объект без условия вида:

```ts
if (project === 'Волковский') { ... }
```

Если это получилось — создан продуктовый механизм.

Если для каждого объекта нужен новый набор ручных исключений — создана автоматизация одного Excel-пакета.

---

## 17. Решение для команды

На текущем этапе рекомендуется принять пять решений:

1. считать CAUDEX baseline первого product contour;
2. не развивать новые agent/crew функции до release gate MVP;
3. реализовывать новый contour рядом с legacy flow, без big-bang rewrite;
4. использовать AI только на неопределённой границе данных и для explanation;
5. считать успешным не «AI-анализ объекта», а доказуемое сокращение разрыва между выполненной работой и деньгами.

Это оставляет СтройИнтел технически сложным продуктом, но делает эту сложность подчинённой реальной бизнес-задаче, а не наоборот.
