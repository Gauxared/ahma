# CAUDEX — аналитический контур СтройИнтел

> Рабочая область бизнес- и системного анализа.  
> `ahma` — техническое имя репозитория; в документах используем название продукта **СтройИнтел**.

## Зачем существует эта папка

Текущий СтройИнтел уже содержит заметный объём кода, расчётных модулей, конфигурации, интерфейсов и LLM-оркестрации. Проблема следующего этапа — не в нехватке функций, а в необходимости зафиксировать, **какой бизнес-процесс система автоматизирует, на каких данных строит выводы и где заканчивается алгоритм и начинается экспертное суждение**.

CAUDEX не является ещё одним runtime-слоем приложения. Здесь фиксируются решения аналитика до того, как они превращаются в код, конфигурацию или интерфейс.

Базовый порядок работы:

`бизнес-процесс → решение пользователя → необходимые данные → правила и состояния → автоматизация → интерфейс`

Не наоборот.

## Рабочая гипотеза продукта

Первый целевой контур СтройИнтел:

**контроль выполнения и монетизации строительных работ.**

Основной управленческий вопрос:

> Что физически выполнено на объекте, что из этого подтверждено первичкой, что готово к предъявлению, что уже подписано и оплачено — и что мешает следующему переходу?

Каноническая цепочка первого MVP:

`Запланировано → Выполнено → Подтверждено → Предъявлено → Подписано → Оплачено`

Если переход не может быть доказан входными данными, система должна назвать недостающий документ или факт, а не достраивать его предположением.

## Архитектурный принцип AI

**AI работает на грязной границе системы; внутри — нормализованные данные и детерминированные правила.**

Предпочтительный порядок обработки:

1. структурный парсер;
2. нормализация;
3. правила и точное сопоставление;
4. fuzzy matching;
5. LLM/ML только там, где предыдущие уровни не дают надёжного результата.

LLM допустим для извлечения структуры из слабоструктурированного текста, семантического сопоставления и объяснения уже рассчитанного результата. Деньги, проценты готовности, сроки, EVM, кассовые показатели и итоговые статусы должны рассчитываться кодом по зафиксированным правилам.

## Что сохраняем из текущего СтройИнтел

Существующее ядро не рассматривается как одноразовый прототип. В первую очередь повторно используем:

- `modules/calculations/` — детерминированные расчёты и тесты;
- `config/formulas/registry.json` — реестр формул и traceability;
- реестры параметров и reference cases;
- document/intake-парсеры;
- принцип `unknown != 0`;
- provenance/source trace;
- ports/adapters и архитектурные проверки.

При этом до фиксации продукта **замораживается расширение количества LLM-ролей, orchestration-режимов и демонстрационных экранов**. Новая функция должна быть привязана к конкретному пользовательскому решению и источнику данных.

## Первый эталонный объект

**Волковский ГОК** используется как первый reference case, потому что по нему уже есть связанный пакет материалов:

- штабной статус;
- ЦИМ с план/фактом, ОЖР, БДДС и реестрами;
- актуализированный КСГ;
- HTML-дашборд;
- текущая спецификация «аналитического слоя»;
- реализация СтройИнтел в репозитории.

Цель анализа — не автоматизировать именно Волковский, а выделить инвариантный процесс, который переживёт второй и третий объект без объектных `if` и ручных исключений в коде.

## Definition of Done первого продуктового контура

Для каждой работы система должна уметь доказуемо определить:

- плановый объём и единицу измерения;
- фактический выполненный объём;
- источник подтверждения факта;
- готовность к предъявлению;
- факт предъявления/подписания;
- факт оплаты;
- текущий blocker перехода;
- возраст blocker;
- денежный эффект зависшей работы, если он вычислим.

Либо система должна явно назвать, **каких данных не хватает для ответа**.

## Следующий пакет

До передачи production-реализации агенту остаётся два документа верхнего уровня:

- `12_TARGET_ARCHITECTURE.md` — короткая целевая архитектура первого контура с границами модулей и потоками данных, без изобретения новой платформы;
- `13_ANALYTICS_SUMMARY.md` — человекочитаемая сводка для коллеги/руководства: проблема, продуктовый поворот, место AI, MVP, что сохраняем и что перестаём развивать.

После их фиксации Codex подключается сначала **в read-only режиме как технический аудитор** по заданию из `10_CURRENT_CODE_MAPPING.md` / `11_DELIVERY_BACKLOG.md`, а не как автор новой продуктовой архитектуры.

## Правило изменений

Любое предложение по развитию СтройИнтел должно отвечать минимум на четыре вопроса:

1. Кто принимает решение?
2. Какой факт ему нужен для решения?
3. Из какого первичного источника этот факт получается?
4. Почему для этого нужен новый код/AI/экран, а не существующий механизм?

Если ответы не определены, задача остаётся аналитической и в разработку не передаётся.
