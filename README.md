# СтройИнтеллект

Система проверки строительной сметной документации. На вход — папка или архив с
файлами объекта: сметы, чертежи, договоры, пояснительные записки. На выходе —
вердикт, замечания со ссылкой на строку исходного файла и пакет из десяти
документов, который заказчик уносит со встречи.

Этот файл объясняет, **как система устроена и что происходит внутри одного
прогона**, человеку, который не открывал исходный код. Инструкция для того, кто
будет работать через интерфейс, — в конце, в разделе «Работа через интерфейс».

---

## 1. Что система делает, в одном абзаце

Подрядчику приносят комплект документов по объекту. Внутри — локальные сметные
расчёты на сотни позиций, сводный расчёт, чертежи в PDF, договор. Человеку нужно
несколько дней, чтобы понять: сходятся ли числа, нет ли задвоенных расценок, не
завышены ли объёмы, что не подтверждено документами и чем это грозит по деньгам
и по срокам. Система делает первый проход за минуты: **читает документы,
разбирает сметы в позиции, сверяет их с федеральной нормативной базой, считает
сходимость арифметикой, а затем показывает разобранное десяти агентам —
языковой модели в десяти ролях**: сметчик, ГИП, эконом, снабженец, подрядчик,
ПТО, договорник, администратор, руководитель, планировщик. Каждый смотрит на
объект со своей стороны и возвращает замечания, поручения и таблицы.

**Три режима работы.** `Конвейер` — каждая роль отвечает одним вызовом по
подготовленному материалу: быстро и дёшево. `Агентный` — агент получает
ИНСТРУМЕНТЫ и решает сам, что прочитать: позиции сметы, лист книги, норматив по
шифру, страницу документации, пересчёт сходимости. `Агенты` (экипаж ролей) —
каждая роль живёт в собственном разговоре, получает рабочую папку объекта и
читает исходные файлы САМА, командами оболочки; роли идут тактами 0–4, передают
работу друг другу и возвращают непринятое. Режим выбирается кнопкой при запуске.

**Роль отвечает свободно, а не по схеме.** До 09.09.2026 ответ был строгим JSON
из шестнадцати обязательных полей — форма решала за роль, что сказать. Теперь
роль пишет документ так, как учит её собственный промпт, а система извлекает
структуру для экрана и пакета по маркерам, которым роль обучена Ядром: значок
вердикта, `[ИСТОЧНИК: документ, дата, статус]`, `❌ НЕИЗВЕСТНОЕ`, «БЛОК ДЛЯ
[ИМЯ]», «🚨 АЛЕРТ», «НЕ ПРИНИМАЮ», таблицы. Текст ответа сохраняется дословно
рядом с разбором: он и есть документ роли.

**Повторный прогон объекта — редакция, а не второй первый взгляд.** Роль
продолжает свой прежний разговор и получает выписку прошлого заключения с
требованием назвать судьбу каждой прежней находки: закрыта, осталась, снята.

**Главное свойство: система не считает деньги моделью и не выдаёт догадку за
факт.** Арифметику считает код, а модель объясняет и находит смысловые
расхождения. У каждого числа в отчёте есть след: из какого файла, с какого листа,
из какой строки оно взято и насколько ему можно верить.

## 2. Технический стек

| Слой | Чем сделано | Почему так |
|---|---|---|
| Интерфейс | **Next.js 16** (App Router), **React 19** серверными компонентами, **Tailwind 4** | Экран собирается на сервере: браузер получает готовую разметку, а не пустую страницу с загрузчиком. Данные не уезжают в клиентский JavaScript |
| Язык | **TypeScript 5** в строгом режиме, включая `exactOptionalPropertyTypes` | «Поля нет» и «поле есть со значением `undefined`» — разные вещи. Различие защищает от подстановки нуля вместо неизвестного |
| База | **PostgreSQL 16**, доступ через **Prisma 7** | Изоляция арендаторов — на уровне СУБД (см. ниже про RLS), а не только в коде |
| Фоновые задачи | собственная очередь в той же базе, воркер на **tsx** | Отдельная очередь (Redis, RabbitMQ) — ещё одна система в развёртывании ради одной таблицы задач |
| Разбор книг | **xlsx**, **exceljs** | `xlsx` читает и `.xlsx`, и старый двоичный `.xls`, и `.csv`. Смета в документе Word тоже становится листом: разбор написан над абстракцией листа, а не над Excel |
| Разбор документов | **poppler** (`pdftotext -layout`, `pdftoppm`), **pdf-parse** (запасной путь), **mammoth** (`.docx`), **fast-xml-parser** | Poppler обязателен: в бандле `pdf-parse` нет ни `standardFontDataUrl`, ни `useSystemFonts`, и PDF с невстроенными шрифтами рисуется белым листом — зрение честно отвечает «страница пуста». Он же даёт текст с колонками: на локальном сметном расчёте 125 486 → 462 240 знаков |
| Выгрузка | **exceljs** (книги пакета), **docx** (записка) | |
| Архивы | **jszip**, **node-unrar-js**, **7z-wasm** | ZIP опознаётся и по центральному каталогу в хвосте: у архивов Windows начало файла бывает занято чем угодно. Имена внутри читаются по флагу кодировки — иначе кириллица превращается в мусор |
| Деньги | **decimal.js** | Рубли считаются десятичной арифметикой. Числа с плавающей точкой дают 0,1 + 0,2 = 0,30000000000000004, и в смете это расхождение |
| Пароли | **argon2** | |
| Схемы данных | **zod 4** | Конфигурация проверяется при старте, а не при первом обращении |
| Модель | любой провайдер с **OpenAI-совместимым API**, включая инструменты (`tools`) и зрение | Провайдер меняется адресом в конфигурации; проверено на трёх |
| Проверки | **Vitest 4** (наборы), **Playwright** (сквозные), **axe** (доступность) | |

Пакетный менеджер — **pnpm**. Монорепозиторий без сборочной системы поверх:
рабочие пространства и `tsc`.

## 3. Как устроен код: порты и адаптеры

Код разложен по слоям, и каждый слой знает только о том, что ниже.

```
apps/          что запускается: web (интерфейс), worker (фоновые задачи), cli
   │
platform/      единственное место, знающее о внешнем мире:
   │           база, файловая система, HTTP к моделям, конфигурация
   │
modules/       предметная логика: разбор смет, расчёты, агенты, обход, выгрузка
   │           НЕ знает ни про базу, ни про файлы, ни про сеть
   │
packages/      контракты: типы, которыми слои разговаривают
```

**Почему так, а не «сервисы, которые всё умеют».** Логика проверки объекта —
`modules/workflow/check-object.ts` — не открывает файлы и не ходит в базу. Всё,
что ей нужно, приходит **портами**: «найди документы в папке», «разбери эту
смету», «спроси агента». Порты реализует `platform/execution/check-ports.ts` —
там и файлы, и модель, и база.

Отсюда два практических следствия:

1. Логику вердикта можно проверить без файлов, без базы и без модели — подставив
   портам заранее известные ответы. Так работает большая часть из 1365 наборов.
2. Заменить провайдера модели или хранилище — значит заменить адаптер, а не
   переписать логику.

Границы проверяются автоматически: `pnpm verify:architecture` роняет сборку,
если `modules/` начнёт импортировать `platform/`.

## 4. Ключевые правила, на которых всё держится

Эти правила объясняют многое в поведении системы, поэтому названы отдельно.

**Неизвестное не превращается в ноль.** Если сумма не определена, в отчёте стоит
«величина не определена», а не «0 ₽». Ноль — это утверждение, что нарушение
бесплатно, и оно почти всегда ложное.

**Молчаливый пропуск запрещён.** Любой файл в папке объекта получает либо разбор,
либо **отказ с названной причиной**. Третьего исхода — «ничего не произошло» —
не существует. Именно он даёт зелёный вердикт на неполном обходе.

**Отказ разбора не равен отказу чтения.** Книга не по стандартной форме в позиции
не разбирается (позиции пришлось бы выдумать), но её содержимое читается и
уходит агентам текстом. Экран говорит и то, и другое.

**Числа считает код, а не модель.** Модель называет порядковый номер позиции;
рубли к нему подставляет расчётный модуль из разобранной сметы. Число из ответа
модели — это число без следа.

**Fail closed.** Ошибка конфигурации останавливает старт, а не всплывает на
первой проверке. Адрес модели, не объявленный в `config/extensions/model-routes.json`,
сборку не проходит: куда уходили данные, должно быть видно при разборе.

**Одна строка документа считается один раз.** Смету читают несколько ролей, и
переделка по возврату выписывает строки заново. Позиция сводится по физическому
месту — документ, лист, номер строки: работа, посчитанная дважды, — это работа,
оплаченная дважды.

**Итог документа — не позиция.** «Всего с НДС» рядом с позициями считало бы
документ дважды. Такая строка помечается итогом: видна человеку, в денежные
своды не идёт.

**Вердикт не бывает мягче собственных находок.** «🟢 принимаем» при четырёх
критических находках — не ошибка модели, а свойство языка: фраза «принимаем, НО
не подтверждено» верна целиком, а в сводку попадает только значок. Цвет
пересчитывается по находкам самой роли, её формулировка сохраняется дословно,
подмена объявляется в той же строке.

**Изоляция арендаторов на двух рубежах.** Первый — решение о доступе в коде.
Второй — Row Level Security в PostgreSQL: приложение ходит в базу под
ограниченной ролью, и запрос без установленного арендатора не вернёт чужую
строку, даже если первый рубеж ошибётся.

роль, один вызов, строгая схема ответа. У экипажа ролей устройство другое, оно
описано следом.

                          │
                          ▼

   │  названия организаций, ФИО, адреса заменяются  │
   │  псевдонимами: «Организация-4721».             │

   ┌──────────────── ШЛЮЗ ВЫХОДА ───────────────────┐
   │  адрес объявлен в конфигурации? класс данных   │
   │  разрешён маршруту? расписка об обезличивании  │

### Чем отличается экипаж ролей

Исполнитель роли — **Codex SDK**: у каждой роли свой тред, своя песочница, свои
инструменты. В интерфейсе это имя не показывается — заказчику оно ничего не
говорит, и режим там называется «агенты · экипаж ролей».

**Роль получает не подготовленный материал, а рабочую папку объекта** — исходные
файлы, разобранные сметы, нормативный каталог, свою опорную базу, кейсы прежней
системы — и читает её сама командами оболочки. Что читать и как глубоко, решает
она: `инструменты/документ <файл>` открывает любой файл партии целиком.

**Схемы ответа нет.** Роль пишет документ формой своего промпта; система
извлекает структуру по маркерам Ядра, а полный текст сохраняет дословно рядом с
разбором (`выход/<Имя>.md`). Строгая схема осталась только на конвейерном пути,
описанном выше.

**Роли идут тактами и передают работу друг другу.** «БЛОК ДЛЯ [ИМЯ]» уходит во
вводную адресата; «НЕ ПРИНИМАЮ» запускает повторный ход того, чей результат не
приняли, и в пакет уходит исправленная редакция. Замерено на прогоне 09.09.2026:
21 возврат и 9 переделок за один прогон.

**Повторный прогон объекта — редакция.** Роль продолжает прежний разговор и
получает выписку своего прошлого заключения: по каждой прежней находке она
обязана сказать, закрыта та, осталась или снята.

**Куда физически уходит запрос.** Шлюз проверяет **назначение** — адрес, ради
которого данные покидают контур. Сам путь до этого адреса может идти через
туннель: провайдеры моделей блокируют адреса части хостингов, и на
`app.strintel.ru` выход настроен через локальный вход sing-box. Хост туннеля
видит трафик до выхода, поэтому туннель не остаётся особенностью одной машины:
он записан в `.env.deploy.example`, назван в `config/extensions/model-routes.json`
и объяснён в `deploy/README.md`. Подробности и две ловушки, на которых это
ломается молча, — там же.

### Откуда берутся листы в книгах пакета

Источника два, и это главное решение в устройстве отчёта.

- **Каркас роли** объявлен в `config/agents/<агент>/manifest.json`. Это то, на
  что роль отвечает **при любом объекте**: сметчик — про сходимость, ценовую базу
  и нормативы НР/СП; договорник — про правовой паспорт и реестр рисков. Двадцать
  три листа на девять ролей. Шапка задана там же.
- **Предметные листы** выбирает агент, **увидевший конкретный объект**. Ни имён,
  ни колонок в конфигурации нет.

Почему не задать все листы конфигурацией: эталонный образец снят с одного
объекта, и лист «Контактная сеть: смета против физики» осмыслен на
железнодорожном переезде и бессмыслен на жилом доме. Агент, обязанный заполнить
лист, которого объект не содержит, начнёт его выдумывать — а выдуманная таблица
выглядит ровно так же, как посчитанная.

Проверено двумя разными объектами: каркас воспроизвёлся полностью на обоих,
предметные листы совпали лишь в пяти случаях из сорока шести.

## 6. Что получается на выходе

**Экран.** Вердикт, ход прогона по шагам, 3–5 сильных выводов, все замечания с
отбором по важности, доска агентов, реестр поручений, документы объекта с
разобранными позициями.

**Пакет из десяти документов** — то, что уносят со встречи:

| № | Документ | Автор |
|---|---|---|
| 01 | Итоговая записка (`.docx`) | Руководитель |
| 02 | Инженерное заключение | ГИП |
| 03 | Сметный анализ | Сметчик |
| 04 | Себестоимость и финрезультат | Эконом |
| 05 | Снабжение и поставки | Снабжение |
| 06 | Подрядный анализ | Подряд |
| 07 | ПТО и исполнительная документация | ПТО |
| 08 | Договорной анализ | Договорник |
| 09 | Организационный протокол | Администратор |
| 10 | График производства работ | Планировщик |

Каждая книга устроена одинаково: **вердикт с главными находками по денежному
весу → предметные листы → замечания → предметы → поручения → «Чего в этом
документе нет»**. Последний лист — не формальность: он называет границы прямо в
документе, который читает заказчик.

**Цепочка доказательности.** У замечания о строке сметы есть: сумма, лист,
строка, имя файла, версия документа и уровень доверия — «факт» для разобранного
из файла, «ориентир» для прочитанного зрением. Нажатие на вывод открывает **ту
версию файла, которую проверяли**, с подсвеченной строкой.

У вывода об объекте целиком координаты нет, и это сказано словом, а не скрыто.

## 6а. Сканы и таблицы из PDF

**Скан читается.** PDF без текстового слоя рендерится постранично в изображения
и читается зрением модели. Раньше это был отказ со ссылкой на условие договора;
6 сентября 2026 требование изменилось — распознавание обязательно, даже внешней
моделью.

**Таблица из PDF становится строками**, а не абзацем: спецификация или ведомость
раскладывается по полям — номер, шифр, наименование, единица, количество, сумма.

**И то, и другое идёт уровнем доверия «ориентир», а не «факт».** Разница
существенна: у разобранного из файла есть лист и строка, его можно открыть и
показать пальцем; у прочитанного с картинки есть только номер страницы.
Подменять одно другим значило бы обесценить весь след.

Поэтому смета, которую можно разобрать по стандартной форме, разбирается ею, а
не читается зрением. Зрение — для того, чего иначе не прочесть вовсе.

**Страницы рисует poppler.** Замерено 09.09.2026 на кейсе «Благоустройство»:
шрифты в документе не встроены, и прежний рендер отдавал страницы 6 и 10 одним и
тем же белым файлом в 6 589 байт. Зрение честно отвечало «страница пуста», и это
выглядело фактом документа, а было нашим сбоем. Тот же лист poppler рисует
целиком — 668 506 байт, таблица позиций с шифрами ГЭСН и суммами.

Страница, которую распознать не удалось, **называется**: «не прочитано N
страниц» с причиной. Молчание превратило бы наш сбой в утверждение «в
спецификации этого нет».

## 6б. Смета любой вёрстки

Форма приказа Минстроя № 421/пр — не единственная, какой присылают смету.
Замерено на клиентском корпусе: из ста настоящих книг по ней составлены
тридцать четыре. Остальные шестьдесят шесть — смета контракта по 44-ФЗ,
ведомость объёмов, калькуляция своей вёрстки, расчёт НМЦК.

**Такая книга разбирается по ШАПКЕ КОЛОНОК** — по заголовкам граф, а не по
шаблону формы. Так читает человек: он не помнит номер приложения, он смотрит,
где написано «Наименование», где «Кол-во», где «Сумма».

**Выбор денежных колонок подтверждается арифметикой самого документа.** Слово
«стоимость» стоит и над ценой единицы, и над суммой; «всего» — и над
количеством с коэффициентами, и над деньгами. Ошибиться колонкой значит выдать
цену за сумму и занизить смету в сотни раз — молча и правдоподобно. Поэтому
среди колонок-кандидатов берётся та тройка, на которой сходится сам документ:
количество × цена = сумма. Что именно прочитано, написано замечанием к
документу: «наименование C, количество E, цена F, сумма G; сошлось на 3 строках
из 3».

**Читаются все листы книги, а не первый.** Смета сплошь и рядом лежит вторым
листом, а первым идёт титул или расчёт индексов — такая книга давала ноль
позиций при живом разборе. То же у документов Word: листом становится каждая
таблица, а не только самая крупная.

Замер 09.09.2026 на трёх кейсах заказчика («Дагестан дороги», «Благоустройство»,
«Самара»), 62 файла: **было 0 позиций, стало 5 900** из 14 файлов.

## 7. Что система НЕ делает

Названо прямо, потому что умолчание читается как обещание.

- **Не разбирает XML ГРАНД-Сметы в позиции** — нет образца схемы. Файл читается
  текстом и помечается «не разобран» с причиной. Опознаётся он теперь верно: до
  09.09.2026 выгрузка с русским корнем `<Смета>` не опознавалась НИКОГДА —
  граница слова `\b` в JavaScript считается по ASCII.
- **Не берёт позиции из скана сметы.** PDF читается листом через раскладку
  колонок, но чтение обязано подтвердиться арифметикой самого документа:
  количество × цена = сумма. У распознанного скана она не сходится — «488 310,74»
  приходит как «488 3^0,74», — и разбор отказывается. Замерено на кейсе
  «Благоустройство»: без этой проверки вышло бы 334 «позиции» с объёмом 625905
  там, где в документе 6,25905. Выдуманная цифра хуже отсутствующей: она
  выглядит фактом. Такой документ идёт ролям текстом и отрисованными
  страницами.
- **Не заменяет человека.** Каждый вывод — повод проверить, а не решение. Поэтому
  в каждом документе есть лист поручений: что проверить, кому, к какому сроку.
- **Не гарантирует одинаковое число замечаний** от прогона к прогону. Разбор,
  арифметика и вердикт воспроизводятся; количество замечаний колеблется в
  пределах примерно полутора раз — это свойство языковой модели.

## 8. Запуск на своей машине

Нужны: Node.js 22+, pnpm, Docker (для PostgreSQL), доступ к модели с
OpenAI-совместимым API.

```bash
pnpm install
docker compose up -d postgres          # база на 127.0.0.1:5432
cp .env.example .env                   # заполнить адрес и ключ модели
pnpm db:migrate                        # применить миграции
pnpm demo:up                           # арендатор, пользователи, объект

pnpm build:web && pnpm start:web       # интерфейс на localhost:3000
pnpm worker                            # в отдельном окне: фоновые задачи
```

Воркер обязателен: интерфейс ставит задачу в очередь, а выполняет её воркер. Без
него проверка останется в состоянии «поставлена в очередь».

**Настройка модели** — четыре переменных в `.env`:

```
STROYINTELLECT_MODEL_BASE_URL=https://openrouter.ai/api/v1
STROYINTELLECT_MODEL_API_KEY=...
STROYINTELLECT_MODEL_ID=openai/gpt-5.6-luna
STROYINTELLECT_VISION_EXTERNAL=да        # согласие отправлять листы чертежей
```

Смена провайдера требует **двух** правок: переменной и объявления адреса в
`config/extensions/model-routes.json`. Одной переменной недостаточно намеренно —
сборка остановится с объяснением.

**Проверки:**

```bash
pnpm verify        # типы, границы слоёв, контраст, наборы (09.09.2026 — 1579 проверок)
pnpm test:e2e      # 146 сквозных проверок в браузере
```

**Пятнадцать наборов требуют настоящей базы** и без неё сообщают об ошибке
подключения, а не притворяются пройденными: изоляцию арендаторов под RLS и запись
хода прогона нельзя проверить на заглушке. Поднять базу — `docker compose up -d
postgres` и `pnpm db:migrate`.

**Поставить Проверку из командной строки** (тем же кодом, что и веб):

```bash
npx tsx tooling/start-check.ts --object <шифр> --tenant <uuid> --mode агенты \
  [--create "Название нового объекта"]
```

## 9. Работа через интерфейс

Раздел для того, кто пользуется системой, а не разрабатывает её.

### 9.1. Вход

Три поля: **арендатор**, **почта**, **пароль**. Арендатор — код организации;
у каждой организации свои объекты, и увидеть чужие нельзя.

Две роли:

- **Администратор** — заводит объекты, загружает файлы, запускает проверки,
  выдаёт доступ клиентам, видит журнал.
- **Клиент** — видит объекты, которые ему открыли, читает результаты и скачивает
  пакет. Запускать проверки и менять доступ не может.

### 9.2. Путь от файлов до пакета — шесть шагов

Наверху экрана объекта всегда виден шаговик: **Объект → Загрузка → Разбор →
Прогон → Вердикт → Пакет**. Он показывает, где вы находитесь.

**Шаг 1. Завести объект.** «Реестр» → форма «Новый объект»: шифр (попадёт в
адрес страницы), наименование, регион. После создания система сама приведёт на
загрузку.

**Шаг 2. Загрузить файлы.** Кнопка «Выбрать файлы» → «Загрузить».

- Принимаются `.xlsx`, `.xls`, `.pdf`, `.docx`, `.xml`, `.csv`, `.txt` и архив
  `.zip`.
- Архив распаковывается **с сохранением структуры папок**; путь файла внутри
  архива виден потом в ссылке замечания.
- Ограничения: до 32 МБ на файл, до 300 файлов за раз.
- Загрузка создаёт **партию**, названную временем. Повторная загрузка не
  затирает предыдущую: партия неизменна, и прогон всегда ссылается на конкретный
  комплект.

**Шаг 3–4. Запустить проверку.** В строке партии — две кнопки:

- **«Проверить»** — полный прогон: разбор плюс все агенты. На комплекте из
  7 файлов это 6–12 минут.
- **«Быстрый»** — только сметный разбор. На ста сметах даёт результат за
  ~8 минут вместо ~45. Экран честно скажет, кого не звали.

Пока идёт прогон, экран не молчит: видно текущий этап словами, счётчик
разобранных документов и ленту агентов. **Первые находки появляются на первой-
второй минуте** и помечены «предварительно» — прогон ещё идёт.

**Шаг 5. Прочитать результат.** Рабочий экран проверки:

- **вердикт** и из чего он сложился;
- **«Что показать клиенту»** — 3–5 сильных выводов. Правило отбора написано
  рядом: тяжёлое сверху, внутри важности — по сумме позиции, одна позиция даёт
  одну находку, один автор — не больше двух;
- **все замечания** с отбором по важности (отбор виден в адресе страницы, так
  что отобранный список можно прислать ссылкой);
- **доска агентов** — кто что сказал; плитка агента, который не работал, ссылкой
  не притворяется;
- **поручения** — что проверить человеку, с адресатом и сроком.

**Как дойти до первоисточника.** У замечания со следом написано, например,
«лист «ЛСР», строка 240 →». Нажатие открывает **ту версию файла, которую
проверяли**, с подсвеченной строкой и разобранными позициями. Это и есть ответ
на вопрос «откуда система это взяла».

Если следа нет — так и написано: «замечание к строке не привязано». Это выводы об
объекте целиком, и привязывать их не к чему.

**Шаг 6. Скачать пакет.** Вкладка «Пакет»: десять строк, у каждой либо кнопка
скачивания, либо названная причина, почему документ не собран. Файлы называются
по-русски, с именем объекта: `01_Итоговая_записка_<объект>.docx`.

Каждое скачивание записывается в журнал.

### 9.3. Выдать доступ клиенту

«Доступ» → добавить пользователя, выбрать право:

- **чтение** — видит результаты, скачивает пакет;
- **запуск проверок** — дополнительно может запускать прогоны.

Клиент другой организации ваших объектов не увидит ни в списке, ни по прямой
ссылке.

### 9.4. Что делать, если что-то пошло не так

| Что вы видите | Что это значит | Что делать |
|---|---|---|
| «Проверка поставлена в очередь» и ничего не меняется | не запущен воркер | запустить `pnpm worker` |
| у файла «отказ», но написано «содержимое прочитано и передано агентам» | в документе не нашлось таблицы с шапкой колонок: пояснительная записка, договор, протокол | ничего; текст агенты прочитали целиком |
| «не поддержан» у PDF | скан без текстового слоя | скан читается зрением модели уровнем доверия «ориентир» (§6а); если позиции нужны фактом — прислать смету книгой |
| «нечего проверять» | не было НИ разбора смет, НИ заключений ролей | если роли высказались, вердикт таким не будет: до 09.09.2026 он появлялся при 85 находках, потому что считал только сметы формы 421/пр |
| «Проверка в очереди» и непонятно, сколько ждать | воркер один, впереди чужие прогоны | на карточке проверки написано, сколько проверок впереди; выпуск нового кода при этом воркер не трогает, пока он ведёт задачу |
| в пакете «не собран» | агент этого документа не высказался | причина написана в подсказке к строке |
| прогон идёт дольше 30 минут | сто и более смет | запускать «Быстрый»: полный разбор всех смет за ~8 минут |

### 9.5. Чего ожидать, а чего не стоит

**Воспроизводится от прогона к прогону:** состав разбора (сколько документов,
смет, позиций, сколько сопоставлено по шифру), арифметика, вердикт, цепочка до
строки, состав пакета и каркас листов каждой роли.

**Колеблется:** количество замечаний и сколько из них критичные — в пределах
примерно полутора раз. Это свойство языковой модели, а не сбой. Обещать клиенту
число замечаний не следует; обещать вердикт и разбор — можно.

**Развёрнуто: `https://app.strintel.ru`** — вход, объекты, все прогоны, вердикты,
замечания со ссылкой до строки исходного файла, скачивание всех десяти
документов пакета. Порядок развёртывания, юниты systemd и блок nginx — в
`deploy/`.

**Рядом стоит стенд — `stage.strintel.ru`, ветка `stage`** (поднят 10.09.2026).
Появились пользователи, и пробовать правки на боевом контуре стало нельзя:
работа идёт на стенде, прод обновляется управляемо, раз в неделю, одной
командой `deploy/promote.sh` — переводом `main` на `stage` без слияния.

Контуры разведены по восьми значениям сразу (корень, ветка, порт, две службы,
кластер базы, имя базы, каталог документов); все восемь названы один раз в
`deploy/contours.sh`, и `tooling/deploy-release.test.ts` останавливает сборку,
если хоть одно совпало. Кластер базы у стенда отдельный не ради порядка: роль
приложения в PostgreSQL принадлежит кластеру, и общий кластер означал бы один
пароль на боевую и стендовую базу.

**Прогонов в боевой базе:** 72 конвейером, 20 собственным агентным циклом,
**15 экипажем ролей**, 2 быстрым проходом.

**Два последних прогона экипажа** (09.09.2026, каждый — комплект тендерной
документации без единой сметы формы 421/пр):

| объект | время | ролей | находок | позиций в базе |
|---|---|---|---|---|
| DG-2 «Дагестан 2» | 63 мин | 11 | 85 | 50 |
| YO-1 «ОСК Йошкар-Ола» | 66 мин | 11 | 86 | 43 |

Позиции здесь целиком выписаны ролями: разбор формы 421/пр не берёт ни один файл
такого комплекта. До 08.09.2026 таких позиций в базе было **ноль** — они
терялись на пути от роли к системе.

**Сверка с эталоном легаси** по кейсу «Йошкар-Ола»: контрольные числа совпали до
рубля — НМЦК 4 002 854 177 ₽, итого с непредвиденными 3 306 403 758 ₽, НДС 22 %
721 826 163 ₽. Подробности и расхождения — в `docs/отчёт-08-09-2026.md`.

**Выход к модели** — `llm.govard.ru/v1` напрямую, туннель отключён. Точки
доступа, блокирующие адрес сервера по IP (`openrouter.ai`, `api.openai.com`,
`api.anthropic.com`), по-прежнему недоступны, но система на них не работает.

**Выпуск не рвёт идущий прогон:** `deploy/release.sh` всегда обновляет интерфейс,
а воркер, ведущий задачу, не перезапускает и говорит об этом вслух. Прогон
экипажа идёт до часа и стоит миллионы токенов — обрывать его выпуском нельзя.

**Что разобрано и что осталось.** За 8–9 сентября 2026 разобрано двадцать четыре
класса дефектов: пять из них оказались ложной тревогой, остальные закрыты с
замером до и после. Перечень — `docs/spec-demo-stage-1-fact.md` §5а. Классы,
которые ещё предстоит проверить, и порядок работы с ними —
`docs/spec-demo-stage-1.md` §14а.

Открытые ограничения с названными причинами — `docs/spec-demo-stage-1-fact.md`
§7. Каждая строка там объяснена одним из четырёх видов причин: не успел, требует
решения владельца, не хватает данных извне, внешнее ограничение.
