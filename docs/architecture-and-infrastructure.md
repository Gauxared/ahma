# СтройИнтеллект: архитектура и требования к инфраструктуре

**Дата:** 01.09.2026
**Состояние:** M0–M5 закрыты, M6 в работе
**Область:** этап 1 — демонстрационная версия на моделях по API
**Основание:** ТЗ §6.1–6.4, §11, §15.1; роадмап M0–M7; ADR-R-015, R-017, R-020

---

## 1. Что это за документ

Здесь описано, **как система устроена сейчас**, **что добавляется к
демонстрации** и **какое железо для этого нужно**.

Документ разделён по этапам, и это не формальность. Этап 1 — демонстрационная
версия на моделях по API: ускорителей не требуется вовсе. Этап 2 — переход на
локальные модели: **отдельная работа на отдельном железе**, и требования §6.2 к
узлу вывода относятся к ней, а не к сегодняшнему дню.

Смешивать эти два набора требований — значит просить сегодня деньги за железо,
которое понадобится через квартал.

---

## 2. Два этапа и граница между ними

### 2.1 Решение

ADR-R-020 фиксирует его дословно: «вся функциональность отрабатывается на внешних
моделях, перевод на локальные выполняется после того, как результат устойчив».

| | Этап 1 — демонстрация | Этап 2 — контур Заказчика |
|---|---|---|
| Модели | внешние, по API | локальные, с открытыми весами (§6.3) |
| Ускорители | **не нужны** | ≥80 ГБ видеопамяти (§6.2) |
| Где живёт | наш сервер | контур АПРИ |
| Кто эксплуатирует | мы | Заказчик (§6.2) |
| Профиль | `development` / `single-tenant-onprem` | `single-tenant-onprem` |
| Данные | курганский кейс, корпус 7КЛ, анонимизированное | боевые |
| Узел вывода | — | отдельный сервер, отдельная история |

### 2.2 Что делает переход между этапами сменой конфигурации, а не переписыванием

Главный риск перехода — не внешние модели сами по себе, а **незаметная опора на
их возможности**. Если девять агентов созреют на фронтирной модели с большим
контекстом и безупречным следованием инструкции, «перевод в контур» окажется
переписыванием промптов, а не сменой адреса.

Механизм против этого **уже работает**: `config/model-profiles/target-local.json`
объявляет потолок целевой локальной модели, и адаптер применяет **его**, а не
фактический потолок провайдера:

```json
{ "contextWindow": 32768, "maxOutputTokens": 8192,
  "structuredOutput": "json_schema", "toolCalling": "prompted", "vision": false }
```

То есть на внешней модели мы уже сегодня работаем внутри ограничений локальной.
Это делает этап 2 сменой конфигурации — и это единственная причина, по которой о
локальных моделях можно сейчас не думать.

### 2.3 Небольшая локальная модель для замера разрыва — это не узел вывода

ADR-R-020 требует вести метрику «разрыв между внешней и целевой моделью» с M3.
Для замера нужна **небольшая** локальная модель — она помещается на машине
разработчика или на арендованном по часам ускорителе.

Путать её с узлом вывода промышленного класса не надо: первое стоит десятки
рублей в час по мере надобности, второе — миллионы единовременно.

Механизм замера готов и работает: `si eval --shadow`.

## 3. Граница по данным: главное ограничение демонстрации

Это не формальность, а единственное безусловное «нельзя» в проекте.

ТЗ §12.1л и ADR-R-020: **сведения АПРИ, составляющие коммерческую тайну, в
исходном виде за пределы контура не передаются ни при каких режимах работы.**
Внешняя модель на коммерческой тайне вне подписанного Регламента запрещена
безусловно.

Для демонстрации на API-моделях это означает выбор из трёх, и его надо сделать
явно:

| Вариант | Что можно показать | Чего требует |
|---|---|---|
| Курганский кейс и корпус 7КЛ | полный сквозной путь на настоящих сметах | ничего: вопрос внешнего контура не возникает |
| Анонимизированные документы АПРИ | тот же путь на их данных | процедура анонимизации (M7) |
| Боевые документы АПРИ | всё | **подписанный Регламент передачи данных** (§8.3, результат этапа 1) |

Сегодня работает первый вариант: курганский объект, КП подрядчика SLK,
закупочный фон из открытых прайсов. Этого достаточно для демонстрации всех
функций.

**Журнал внешних вызовов — черновик договорного артефакта.** Каждый вызов
классифицируется по процессу, классу данных и назначению
(`platform/runtime/call-journal.ts`). §12.1л проверяется именно записями журнала,
и журнал периода разработки прямо становится основой Регламента.

## 4. Текущая архитектура

### 4.1 Слои

```
packages/contracts     узкая талия: типы, провенанс, единицы,
   (1 084 строки)      нормализация текста, экранирование
        │              — единственное, что модули знают друг о друге
        ▼
modules/               доменная логика, БЕЗ побочных эффектов
   (18 413 строк)      agents · calculations · canonical · corpus
        │              documents · eval · exports · intake · workflow
        ▼
platform/              всё, что трогает мир
   (6 473 строки)      db · queue · security · storage · runtime
        │              config · execution · extensions · jobs
        ▼
apps/                  точки входа
   (6 126 строк)       cli · web · worker
```

Правило талии проверяется машиной: `tooling/verify-architecture.ts` валит
сборку, если модуль импортирует внутренности соседнего модуля, если доменный
модуль тянет фреймворк, если формула не объявлена в реестре или если ставка
задана литералом. Это гейт, а не соглашение.

### 4.2 Что работает сегодня

**Расчётное ядро.** Четырнадцать формул §6.4 в реестре
`config/formulas/registry.json`. Каждое число выходит наружу только с `SourceRef`
или `FormulaTrace` — обеспечено типом.

**Разбор документов.** Определение формата по содержимому, а не по расширению;
реестр адаптеров без пустой ветки `default`; xlsx (ГРАНД-Смета 421/пр), docx,
PDF с проверкой текстового слоя (§14: сканы отклоняются явным статусом).

**Сопоставление КП.** Текстовый путь канонизации: приведение к основе слова,
синонимы из конфигурации, три исхода, агрегация состава, журнал подтверждений с
хранением обеих версий. На настоящем КП — 8 сопоставлений из 9, девятое —
правильный отказ.

**Девять агентов и приёмка.** Протокол тактов, гейты на общих предметах,
ограниченный цикл возвратов, приёмка §12.2 по каждому агенту, режимы глубины
§5.4, теневой прогон.

**Выгрузки.** Все четыре по §10, с экранированием формульных инъекций в писателе
книги.

**Безопасность.** Изоляция арендатора двумя рубежами (`PolicyDecisionPoint` и
RLS), роли из конфигурации (§4), сессии с хранением токена хэшем, вход с
проверкой источника, журнал, **неизменяемый на уровне базы**.

**Очередь.** На PostgreSQL с арендой, идемпотентностью, отсрочкой повторов и
отменой. Восстановление после падения воркера — истечение аренды.

**823 теста**, включая прогоны против настоящего PostgreSQL с RLS и против
настоящих документов Заказчика.

### 4.3 Чего сегодня нет

| Не готово | Следствие |
|---|---|
| Исполнители задач в воркере | очередь работает, выполнять задачу некому |
| Четыре из шести экранов §5.5 | есть реестр объектов, карточка, журнал |
| Запись из веба | проверки запускаются командной строкой |
| Egress-шлюз | манифесты объявляют назначения, принуждения нет |
| Анонимизация | вариант «демо на данных АПРИ» пока закрыт |
| StorHaus, релизный набор | M7 |
| Объектное хранилище | документы читаются с диска |

## 5. Что нужно доделать к демонстрации

Порядок — по тому, что раньше становится видно снаружи.

1. **Исполнители задач в воркере.** Порты проверки выносятся из
   `checkObjectCommand` в общий модуль. После этого веб ставит задачу, воркер её
   выполняет — §5.6 становится правдой.
2. **Экран загрузки и разбора** с предпросмотром позиций и ручной правкой.
3. **Экран сравнения предложений** — расчёт готов, нужен экран.
4. **Рабочий экран** выбора агента и режима.
5. **Запись из веба**: CSRF на всех формах, проверка прав на каждой операции.
6. **Уведомление о завершении** — минимально опросом состояния экраном.

Egress-шлюз и анонимизация нужны только для варианта «демо на данных АПРИ». Для
демонстрации на курганском кейсе они не требуются.

## 6. Состав контейнеров: этап 1

По образцу Domovey, но короче: без Valkey, без Meilisearch, без узла вывода.

| Контейнер | Назначение | Есть | dev | demo |
|---|---|:--:|:--:|:--:|
| `traefik` | обратный прокси, TLS | нет | — | ✓ |
| `web` | Next.js, экраны §5.5 | частично | ✓ | ✓ |
| `worker` | исполнение проверок | каркас | ✓ | ✓ ×2 |
| `migrate` | миграции до старта | нет | ✓ | ✓ |
| `postgres` | данные, очередь, журнал; RLS | ✓ | ✓ | ✓ |
| `objects` | хранилище документов | нет | — | ✓ |
| `clamav` | проверка документов подрядчиков | нет | — | ✓ |
| `backup` | `pg_dump` по расписанию | нет | — | ✓ |
| `langfuse` (5 шт.) | трассировка вызовов моделей | нет | ✓ | ✓ |
| `mailpit` | перехват почты | нет | ✓ | ✓ |
| `health-watchdog` | перезапуск нездоровых | нет | — | ✓ |

Итого на демо-сервере: **около 13 контейнеров**, ни одного с ускорителем.

**Почему очередь не в Redis.** Отдельный Redis добавляет систему с отдельным
резервным копированием, отдельным доступом и отдельной точкой отказа — ради
нагрузки, которой здесь нет. PostgreSQL даёт ту же гарантию невыдачи одной
задачи двум воркерам, а состояние задачи живёт в одной транзакции с результатом.

**Почему Langfuse здесь можно.** Это наш контур и не боевые данные Заказчика. В
контуре АПРИ (этап 2) он будет запрещён §11: трассировка содержит и промпт, и
ответ. Там его место занимает внутренний журнал вызовов.

## 7. Требования к железу: этап 1

### 7.1 Измерено, а не оценено

Числа ниже получены прогоном на настоящих документах Заказчика, а не расчётом.

| Что | Время | Пик памяти |
|---|---:|---:|
| Проверка курганского объекта: 7 документов, 4 сметы, 101 позиция, 2 PDF рабочей документации | **7,6 с** | **1,1 ГБ** |
| Книга 2,7 МБ (единый документ команды, Йошкар-Ола) | 4,5 с | 0,3 ГБ |
| Книга **39 МБ** (исполнительная документация, генплан) | **94 с** | **4,6 ГБ** |

**Главный вывод из замеров.** Память воркера определяется **самым большим
документом**, а не числом одновременных проверок. Книга на 39 МБ забирает
4,6 ГБ — и такие книги в корпусе Заказчика есть. Воркер, рассчитанный «по
среднему», ляжет на первом же таком файле.

Отсюда: **не менее 8 ГБ на воркер**, а не 2–4, как дал бы расчёт по средней
смете.

Второй вывод: разбор — задача **ЦП и памяти**, а не ускорителя. На этапе 1
ускоритель не нужен вовсе, а на этапе 2 он не поможет разбору: ему достанется
только вывод модели.

### 7.2 Демонстрационный сервер

Один узел, без ускорителя.

| Параметр | Значение | Обоснование |
|---|---|---|
| ЦП | **8 ядер** | разбор книги — одно ядро надолго; 2 воркера + web + postgres + обвязка |
| ОЗУ | **32 ГБ** | 2 воркера × 8 ГБ (см. 7.1) + postgres 4 ГБ + web 1 ГБ + Langfuse ~4 ГБ + запас |
| Диск | **500 ГБ NVMe** | документы, база, копии, образы |
| Сеть | 1 Гбит/с, публичный адрес | доступ к демонстрации и вызовы API моделей |
| ОС | Linux, Docker | §6.2 |

**Почему NVMe, а не SATA.** Разбор книги на 39 МБ — это чтение и распаковка ZIP
с тысячами XML внутри. На SATA те же 94 секунды превращаются в минуты.

**Почему 32 ГБ, а не 16.** Два воркера, способные пережить большой документ, —
это уже 16 ГБ только на них. С Langfuse и Postgres 16 ГБ упрутся в своп, а своп
на разборе книги означает не «медленнее», а «остановилось».

### 7.3 Разработка

| Узел | Конфигурация | Обоснование |
|---|---|---|
| Машина разработчика | 8 ядер, 16 ГБ ОЗУ, 200 ГБ NVMe | PostgreSQL в Docker, сборка, тесты |
| Общий сервер (не обязателен) | 4 ядра, 16 ГБ, 200 ГБ | если нужен общий стенд помимо демо |

Полный набор из 823 тестов на 8 ядрах идёт около 20 секунд, включая прогоны
против настоящей базы. Это тот показатель, ниже которого падать нельзя: набор,
идущий минуты, перестают запускать.

### 7.4 Затраты на внешние модели

КП ограничивает бюджет внешнего контура: **≤20 000 ₽/мес**.

Это операционное ограничение демонстрации, и его надо **измерить, а не
предположить**. Механизм готов: `platform/runtime/call-journal.ts` классифицирует
каждый вызов по процессу, классу данных и объёму.

Что известно сейчас: девять агентов идут по такту, каждый делает десятки вызовов;
потолок контекста ограничен профилем `target-local` (32k вход, 8k выход), то есть
верхняя граница объёма на вызов задана. Стоимость одной полной проверки объекта
измеряется первым же прогоном с включённым журналом — и до этого замера называть
число было бы гаданием.

**Что делать при приближении к лимиту:** режим «экспресс» §5.4 ограничен
15 строками без таблиц и стоит в разы дешевле «эксперта». Демонстрацию можно
вести в «стандарте», оставив «эксперт» для показа на одном объекте.

## 8. Требования к железу: этап 2 (справочно)

Приводится, чтобы отделить от этапа 1, а не для закупки сейчас.

Переход на локальные модели требует **отдельного узла вывода**, и по ТЗ §6.2 его
предоставляет Заказчик (§15.1):

| Узел | Минимум §6.2 |
|---|---|
| Узел вывода моделей | видеопамять ≥80 ГБ на чип; ЦП ≥32 ядра; ОЗУ ≥256 ГБ; NVMe ≥4 ТБ |
| Сервер приложения и БД | ЦП ≥16 ядер; ОЗУ ≥64 ГБ; NVMe ≥2 ТБ |
| Сеть | между узлами ≥10 Гбит/с |

**Откуда 80 ГБ.** Целевой класс модели — 30B, окно 32k. Веса в bf16 — около
60 ГБ; KV-кэш на восемь одновременных запросов при полном контексте — около
32 ГБ. Девять агентов, идущих по такту, дают именно одновременность, а режим
«экспресс» с его 15 минутами не позволяет ставить их в очередь.

**Это не наш сервер и не наша задача сегодня.** Узел вывода — отдельная работа
этапа 2 с собственным выбором модели, квантизации и обвязки.

## 9. Развёртывание

### 9.1 Этап 1

Демонстрационный сервер — наш, поэтому выкладка возможна как в Domovey: GitHub
Actions по SSH, `docker compose` с фиксированным именем проекта и путём.

```
dev ──(тесты, гейты, verify-architecture)──► demo
```

Миграции — отдельным одноразовым контейнером до старта приложения.

**Существенное ограничение, уже проверенное на практике: сброс базы
недопустим.** Миграции пишутся так, чтобы применяться к существующим данным;
переименования делаются отдельной миграцией, а не через `migrate reset`.

### 9.2 Этап 2

Промышленный контур получает **подписанный релизный набор**: архив с образами,
миграциями, конфигурацией и манифестом версий, разворачиваемый на машине **без
доступа в интернет**. Система, которую нельзя развернуть без `docker pull` из
интернета, в закрытом контуре не разворачивается вовсе.

Переход `demo → контур` разрешён **по закрытию разрыва** ADR-R-020, а не по
наступлению срока.

## 10. Открытые вопросы

**Данные для демонстрации.** Курганский кейс достаточен технически. Если нужно
показать на документах АПРИ — требуется анонимизация (M7) либо подписанный
Регламент. Решение продуктовое, и принять его надо до, а не во время показа.

**Хранилище документов.** SeaweedFS или MinIO. Сейчас файлы на диске, для
демонстрации этого хватает.

**Число воркеров.** Два — оценка. Точное число даёт замер: сколько проверок идёт
одновременно и сколько занимает разбор конкретного объекта.

**Уведомление о завершении** (§5.6): опрос экраном, почта или вебхук. Зависит от
того, как Заказчик работает.
