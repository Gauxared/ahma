# Развёртывание демонстрационного стека

**Область:** этап 1 — модели по API, ускорителей нет.
**Основание:** docs/architecture-and-infrastructure.md

---

## 1. Что нужно на сервере

| | Значение |
|---|---|
| ЦП | 8 ядер |
| ОЗУ | 32 ГБ |
| Диск | 500 ГБ NVMe |
| ОС | Linux с Docker и Compose v2 |

Обоснование чисел — §7 архитектурного документа; коротко: книга Excel на 39 МБ
из корпуса заказчика забирает 4,6 ГБ памяти и 94 секунды, и воркер обязан
переживать такой файл, а не средний.

---

## 2. Что НЕ попадает в образ

Документы заказчика. Ни сметы, ни рабочая документация, ни коммерческие
предложения.

Образ может уехать в реестр, а реестр — не место для смет заказчика. Папки
объектов подключаются томом на чтение при запуске. Это не удобство, а прямое
следствие §11: данные остаются там, где им положено.

## 3. Порядок

```bash
git clone <репозиторий> /opt/stroyintellekt
cd /opt/stroyintellekt

cp .env.deploy.example .env
$EDITOR .env          # ИМЯ СТЕКА, пароли, ключ модели, путь к объектам

docker build -t stroyintellekt:dev .
docker compose -f docker-compose.deploy.yml up -d
```

Порядок запуска задан зависимостями: `postgres` → `migrate` → `web` и `worker`.
Приложение не стартует, пока миграции не отработали успешно.

**Имя стека обязательно своё.** `COMPOSE_PROJECT_NAME` у каждой установки
различается: `si-demo`, `si-stage`, `si-apri`. Совпадение имён означает, что
compose переиспользует чужие контейнеры и тома как свои — в лучшем случае это
отказ миграций, в худшем успешная миграция чужой базы. Проверено на практике:
первая версия стека захватила рабочую базу разработчика.

---

## 4. Почему миграции отдельным контейнером

Приложение, умеющее менять схему, обязано иметь на это права. Но именно
ограниченность роли приложения — то, на чём держится изоляция арендатора: RLS
действует на роль, у которой нет права её обойти (ADR-R-015).

Поэтому миграции выполняет **владелец схемы**, одноразовым контейнером, до
старта приложения. Пароли у владельца и у приложения разные, и это не
формальность.

---

## 5. Первый арендатор и пользователи

Экрана управления пользователями §4 в этой версии нет — учётные записи
заводятся командной строкой:

```bash
docker compose -f docker-compose.deploy.yml exec web \
  pnpm si doctor                      # проверка конфигурации
```

Заведение арендатора, пользователей и привязок ролей — отдельная задача
администрирования; до появления экрана делается через `psql` или скрипт.

---

## 6. Остановка и выкладка новой версии

```bash
docker build -t stroyintellekt:dev .
docker compose -f docker-compose.deploy.yml up -d
```

Воркер останавливается по SIGTERM **дорабатывая текущую задачу**: `stop_grace_period`
даёт ему на это две минуты. Убитый на середине воркер оставил бы задачу в
состоянии «выполняется» до истечения аренды — пользователь ждал бы лишние
минуты без причины.

---

## 7. Проверка, что стек живой

```bash
docker compose -f docker-compose.deploy.yml ps
docker compose -f docker-compose.deploy.yml logs -f worker
```

Работающий воркер пишет при старте профиль развёртывания, число источников
знания и число операций. Молчащий воркер без этой строки не запустился.

---

## 8. Резервное копирование

В демонстрационном контуре — наша ответственность; в контуре заказчика по §6.2
её несёт заказчик.

```bash
docker compose -f docker-compose.deploy.yml exec postgres \
  pg_dump -U stroyintellect stroyintellect | gzip > /backup/si-$(date +%F).sql.gz
```

**Журнал восстановить сложнее, чем сохранить.** Записи `audit_event` неизменяемы
для приложения и удаляются только владельцем схемы: копия базы — единственный
способ их вернуть.

## 9. Чего в этом стеке ещё нет

| | Почему |
|---|---|
| `traefik` с TLS | демонстрация идёт по внутренней сети либо за внешним прокси |
| `clamav` | документы приходят от нас, а не от подрядчиков через интерфейс |
| объектное хранилище | документы читаются с примонтированной папки |
| `langfuse` | ставится отдельным стеком, когда нужен разбор вызовов модели |
| `backup` по расписанию | пока командой из §8 |

Каждое из этого добавляется, когда появляется потребность, а не «на всякий
случай»: контейнер, который никто не смотрит, — это ещё одна вещь, которая может
сломаться молча.
