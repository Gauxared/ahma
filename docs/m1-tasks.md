# M1: спецификации задач

Порядок работы по каждой задаче: **спецификация → тесты по спецификации →
реализация → проверка → коммит**. Тесты пишутся до реализации и сначала падают;
задача считается закрытой, когда выполнены все её критерии приёмки, а не когда
код написан.

Общие инварианты, действующие во всех задачах:

- число покидает модуль только как `Valued<T>` с провенансом (ТЗ §9, §12.1д);
- арифметику делает расчётный модуль, модель классифицирует и объясняет (§6.4);
- неизвестное не превращается в ноль: недостающее предъявляется явно (§9);
- операция даёт одинаковый результат из любой точки входа (ADR-R-022);
- модуль разговаривает только узкой талией контрактов (ADR-R-025).

## T1. Приведение позиций к сопоставимому виду

**Зачем.** ТЗ §5.2 требует приводить позиции к сопоставимому виду по
наименованиям, единицам измерения, объёмам и составу работ. Это же нужно
Снабжению для сверки с опорной базой (§5.1). Кодовый путь применим к 97
позициям из 101, поэтому начинаем с него (ADR-R-013).

**Объём.**

1. Реестр единиц измерения с размерным анализом: канонические единицы,
   множители, размерности.
2. Разбор единицы из сметы в каноническую: `100 м2` → `м2` с множителем 100,
   `т` → `кг` с множителем 1000, `шт.` → `шт`.
3. `CanonicalItemRegistry`: справочник видов работ, поиск по нормативному шифру.
4. Отображение позиции ЛСР в `MappedPosition` кодовым путём.

**Критерии приёмки.**

- Все единицы курганского комплекта разбираются либо явно помечаются
  нераспознанными; молчаливого пропуска нет.
- Перевод между разными размерностями запрещён и даёт отказ, а не число.
- Позиция с шифром отображается `by_code`, без шифра — `unmatched` с причиной.
- На курганском комплекте: 97 позиций `by_code`, 4 `unmatched`.
- Количество и сумма выходят как `Valued<Quantity>` и `Valued<Money>`
  с `SourceRef`, указывающим лист и строку.

## T2. Разбор сметы как первоклассная операция

**Зачем.** Пока разбор — это функция, вызываемая тестом. По ADR-R-022 он должен
быть операцией: с предусловиями, идемпотентностью, артефактом и всеми четырьмя
точками входа. Без этого частичное исполнение и обслуживание невозможны.

**Объём.**

1. `OperationDefinition` `parse-estimate`: объявляет требуемые способности,
   варианты, отсутствие предусловий.
2. Реализация операции над `Sheet`, выдающая `Artifact` с телом
   «разобранная смета» и хэшами фактически прочитанных входов (ADR-R-027).
3. `SourceRef` каждой позиции указывает файл, лист и строку.
4. Регистрация в композиционном корне и команда `si run parse-estimate`.

**Критерии приёмки.**

- `si run parse-estimate --file <путь>` печатает сводку и код возврата 0.
- Артефакт содержит `inputHashes` с хэшем содержимого файла.
- Класс полноты `single` при одиночном вызове.
- Операция с неразрешённой обязательной способностью не стартует и называет
  недостающее.
- Повторный прогон на том же файле даёт идентичное тело артефакта.

## T3. Сходимость как операция с провенансом

**Зачем.** §12.1б принимается по выгрузкам, а не по тестам. Сходимость должна
быть операцией, потребляющей артефакт разбора и выдающей артефакт со
значениями, у каждого из которых есть след формулы.

**Объём.**

1. `OperationDefinition` `check-convergence` с предусловием на разобранную смету.
2. Числа результата как `Valued<Money>` с `FormulaTrace`.
3. Сохранение артефакта и следов формул в PostgreSQL в контексте арендатора.
4. Команда `si run check-convergence`.

**Критерии приёмки.**

- На курганском комплекте расхождение 0 ₽, и это видно в выводе команды.
- Ни одно число в артефакте не существует без `SourceRef` либо `FormulaTrace`.
- Расхождение со шкалой ССРСС предъявляется отдельно, с гранулярностью
  и признаком объяснимости.
- Артефакт и следы читаются из базы только в контексте своего арендатора.
- Пустой раздел даёт статус «нечего сверять», а не ложную сходимость.

## T4. Агент Сметчика

**Зачем.** §5.1 требует результата Сметчика, §12.2 принимает его по чек-листу.
Это первый из девяти агентских контрактов и образец для остальных восьми.

**Объём.**

1. Манифест `AgentDefinition` и промпт, портированный из
   `reference-system-new/Выход/Людмила_Сметчик_v9.6.txt`.
2. Строгая схема вывода, проходящая `assertStrictSchema`.
3. Операция `run-agent:estimate-review` над артефактом сходимости.
4. Замер латентности и токенов на реальном объёме позиций.

**Критерии приёмки.**

- Агент возвращает валидный по схеме объект на настоящем endpoint.
- Каждое замечание несёт основание; числа влияния приходят из расчётного
  модуля, а не от модели.
- Прогон укладывается в потолок целевой локальной модели.
- Латентность и токены записаны в журнал обращений.
- Замер на 101 позиции зафиксирован в отчёте: он нужен для оценки §11.

|---|---:|---:|---:|---:|---:|

Суммарно один агент: **94.9 с**, максимум на файл 30.0 с.
Экстраполяция на девять агентов: **14.2 мин** при нормативе §11 «стандарт»
60 минут. Запас есть, но он съедается повторами и более длинными промптами
остальных восьми агентов — замер повторяется на каждом добавленном агенте.

Латентность оказалась заметно стабильнее, чем в спайке M0 (18–30 с против
разброса 5.6–71 с). Вероятная причина — содержательный промпт вместо
тривиального; проверить это отдельно стоит при переходе на локальную модель.

Расход контекста мал: 1.4–1.7 тыс. токенов входа на смету, потому что агенту
передаётся не сама смета, а результат детерминированных проверок. Это тот
самый механизм, который позволит уложиться в потолок 32k целевой локальной
модели на сметах в 2000 позиций.

## T5. Расчётный XLSX

**Зачем.** ТЗ §10 требует Excel с рабочими формулами, листом параметров и
подсвеченными вводимыми значениями. §12.1д требует ноль чисел без маркера
источника в выгрузках.

**Объём.**

1. Построение книги из канонического артефакта, а не из повторного разбора.
2. Рабочие формулы в ячейках итогов; лист «Параметры» с датированными ставками.
3. Подсветка вводимых значений и маркер статуса источника у каждого числа.
4. Экранирование формульной инъекции в пользовательском тексте.

**Критерии приёмки.**

- Каждая формульная ячейка имеет сохранённый `FormulaTrace`.
- Ни одно число не выведено без маркера статуса источника.
- Текст, начинающийся с `=`, `+`, `-`, `@`, экранируется.
- Открытая книга пересчитывается и даёт те же итоги, что и артефакт.
- Метаданные выгрузки содержат версию шаблона, хэш артефакта и версию
  генератора.

## T6. Проверка объекта — гейт MVP

**Зачем.** До сих пор команды работали по одному файлу, а гейт роадмапа
сформулирован по объекту: `si check --object <папка>`. Без него MVP оставался
набором частей: сходимость по каждой смете отдельно не отвечает на вопрос
«принят ли объект».

Это единственный путь, дающий класс полноты `full`: одиночный вызов даёт
`single`, подграф — `partial`, и выдавать их за результат Проверки запрещено
(ADR-R-022).

**Главное свойство.** Обход не теряет документы молча. Смета, которую не удалось
разобрать, попадает в отчёт со статусом «отказ» и проваливает гейт полноты
обхода. Иначе объект с одной нечитаемой сметой отчитался бы зелёным «всё
сошлось» на неполном обходе.

**Определение вида документа.** По имени опознаётся только то, что имеет
название государственной формы (ССРСС) — такие имена устойчивы. Всё остальное,
что является книгой Excel, идёт на разбор как ЛСР, и вид подтверждается
содержанием. Обратное правило (доверять имени) пропустило бы смету с необычным
именем — а пропуск даёт зелёный вердикт на неполном обходе.

  · КУРГАН_СОТ_07.04.2025.pdf          пропущен: рабочая документация
  ✓ РИМ Курган_СОТВ_ … .xlsx           44 поз., по шифру 42, 14 198 884.54 ₽, Δ 0.00 ₽

0 ₽ доказывает, что ни одна позиция не потеряна ПО СУММАМ: пропущенная позиция
дала бы расхождение с итогом раздела. Гейт утверждает именно это — проверяемое
утверждение вместо неподтверждаемого процента.

## T7. Обзор сметчика в составе Проверки

**Зачем.** Роадмап формулирует гейт как `si check --object … --agent estimate_review`.
Без агента Проверка отвечает только на вопрос «сходится ли арифметика», а ТЗ §5.2
требует реестра потенциальных переплат с основанием у каждого пункта.

**Устройство.** Вход агента собирается из ДЕТЕРМИНИРОВАННЫХ проверок, а не из
самой сметы: модель классифицирует и объясняет, арифметику делает расчётный
модуль (ТЗ §6.4). Это же держит расход контекста в пределах потолка целевой
локальной модели.

**Три решения, принятые здесь.**

1. *Запросили обзор и не получили — это отказ.* Если `--agent` указан, а операция
   не собрана (нет endpoint), команда отказывает, а не отдаёт молча
   детерминированную часть под видом полной Проверки.
2. *Отказ агента на одной смете не прерывает обзор остальных,* но попадает в отчёт
   и проваливает гейт агента: иначе объект отчитался бы «принято» без обзора.
3. *Суммы влияния замечаний НЕ складываются.* Сложение денег требует следа формулы
   (§12.1д), а обход — не расчётный модуль. Замечания считаются штуками.

**Вердикт разведён с оценкой сметы.** «ПРОВЕРКА: ПРИНЯТО по критериям §12.1»
отвечает на вопрос «система корректно обработала объект», а не «смета хороша».
Второй вопрос — это замечания сметчика. Слово «принято» без уточнения смешивало
бы их: на курганском объекте Проверка проходит, а сметчик при этом выставляет
критическое замечание на 824 009.97 ₽.

### Результат на курганском объекте (28.08.2026)

Прогон против настоящего endpoint, все четыре ЛСР: **19 замечаний**, у каждого
основание со ссылкой на расчётный модуль. Из них 1 critical, 5 medium, 13 info.

Существенное из найденного:

- **critical** — поз. 89 «Грозозащита для воздушных абонентских линий» на
  824 009.97 ₽ не расшифрована и превышает порог 5% итога;
- **medium** — три потенциальных двойных учёта с совпадением шифра И суммы,
  с точными номерами строк (ГЭСНм08-03-572-06 строки 48 и 148 и другие).

Показательно, что агент удерживает дисциплину основания: там, где данных не
хватает, он пишет «по переданным данным завышение не доказано», а не выдумывает
число. Позиции с одинаковым шифром, но разными суммами он прямо отказывается
считать дублем, называя признак, который не выполнен.

## T8. Сметный разбор по объекту

**Зачем.** MVP определён как «CLI, которая на входе `input-1` воспроизводит
содержательный эквивалент `output-1`» (ADR-R-009). Без выгрузки по объекту
результат Проверки жил только в выводе терминала.

**Объём взят честно, а не по числу листов.** Эталонный лист `03_Сметный_анализ`
содержит 11 листов, но пересчёт индексов, конъюнктурный анализ, финансовый
результат и передачи остальным восьми агентам опираются на данные и модули,
которых пока нет. Клонировать их заглушками — значит выдать пустоту за готовое.

Поэтому в книге пять листов, и пятый — **`05_Не_покрыто`** — строится ВСЕГДА,
даже когда все гейты пройдены. Он отвечает на вопрос «чего в этом документе
нет», чтобы отсутствие раздела не читалось как отсутствие проблемы: ССРСС,
рабочая документация, индексы, конъюнктура, НДС, финрезультат, восемь агентов.

**Четвёртый уровень сходимости.** Три уровня внутри сметы были закрыты
(позиции → раздел → смета → шапка). Добавлен уровень выше: сметы → объект.
Считает расчётный модуль со следом формулы; выгрузка получает готовое значение
и только показывает его.

### Проверка формулы через LibreOffice (28.08.2026)

Книга прогнана через LibreOffice, который пересчитывает формулы при конвертации:

```
104 976 702.48 ₽   СУММА 4 СМЕТ
```

Это ровно та цифра, что стоит в эталонном выходе `output-1`, лист `04_Свод_ЛСР`,
строка «СУММА 4 ЛСР» — сверка с независимым результатом человека, а не с самим
собой. Значение закреплено интеграционным тестом против `KURGAN_SUM_OF_LSR`.

### Границы, поймавшие ошибку

Первая версия выгрузки импортировала типы из `workflow` и функцию сложения из
`calculations` напрямую. `verify-architecture` это отклонил: модули
разговаривают только узкой талией (ADR-R-025).

Исправление оказалось содержательнее формальности. Выгрузка теперь объявляет
свой вход целиком и **ничего не вычисляет**: итог объекта приходит готовым
`Valued<Money>` со следом. Выгрузка, заводящая собственные числа, — это второй
источник правды, который рано или поздно разойдётся с первым.

## T9. Сводный сметный расчёт и второй уровень сходимости

**Зачем.** Роадмап M1 требует двухуровневой сходимости, вторым уровнем называя
«ЛСР → ССРСС» с явным предъявлением расхождения шкалы. Уровень оставался
незакрытым: ССРСС числился пропущенным документом.

**Результат на курганском объекте (28.08.2026).**

```
Итого по Главам 1-9: 104 976.71 тыс.₽ = 104 976 710.00 ₽
Сумма 4 смет:                            104 976 702.48 ₽
Δ 7.52 ₽ при гранулярности шкалы 10 ₽ — объясняется округлением источника
```

Расхождение предъявляется вместе с гранулярностью, а не гасится: инвариант ТЗ §9
работает в обе стороны — выдуманная точность так же недопустима, как потерянная.

**ССРСС — эталон сверки, а не проверяемый документ.** Он не проверяется, он
проверяет. Отдельный статус «сверен», не входит в счётчик проверенных смет и не
участвует в гейте полноты обхода.

**Три ловушки формы, все из настоящего документа.**

1. Заголовок главы лежит в объединённой ячейке и повторён во ВСЕХ колонках
   строки — разбор «непустая A значит позиция» завёл бы его как объект.
2. Под шапкой идёт строка нумерации колонок (A=1, B=2 … H=8), неотличимая от
   объекта по форме. Та же ловушка описана в разборе ЛСР.
3. «Непредвиденные затраты» и «НДС» — начисления процентом от суммы объектов,
   входят в итог ПОСЛЕ неё. Учесть их как объекты значит задвоить. Разводятся
   по обоснованию: у объекта шифр вида «05-02», у начисления — ссылка на норму.
