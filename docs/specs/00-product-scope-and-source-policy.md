# СтройИнтеллект: продуктовый scope и политика источников

## 1. Назначение

Документ определяет границы продукта, порядок разрешения противоречий и правила переноса требований из ТЗ и legacy в модульные спецификации.

`docs/architecture_optimal.md` является кратким архитектурным baseline-индексом. Настоящий документ владеет продуктовым scope и source policy.

## 2. Продуктовая модель

«СтройИнтеллект» — multi-tenant платформа финансово-технического контроля строительства. Платформа принимает документы проекта, нормализует данные, выполняет детерминированные расчёты, запускает применимые аналитические компетенции и формирует проверяемый результат с источниками.

ПАО «АПРИ» является:

- первым pilot tenant;
- договорным контуром первой поставки;
- источником эталонных образцов и контрольного набора;
- базовым сценарием приёмки по исходному ТЗ.

Архитектура не должна ограничивать платформу одной компанией, но platform foundation не расширяет договорный scope АПРИ.

## 4. Классы требований

Каждая запись в requirement и traceability ledgers имеет один класс:

| Класс | Значение |
|---|---|
| `contract` | Буквальное обязательство исходного ТЗ |
| `owner_decision` | Явно утверждённое решение владельца продукта |
| `legacy_rule` | Исполнимое правило работающей legacy-системы |
| `architecture_control` | Необходимый инженерный control |
| `platform_foundation` | Основа для нескольких компаний, не отдельная функция pilot scope |
| `roadmap` | Не входит в текущую договорную приёмку |
| `reference_only` | Источник примера или терминологии |
| `conflict` | Требует решения до реализации затронутого slice |

## 5. Scope первой поставки

### 5.1 Договорный pilot scope АПРИ

- две роли: пользователь и администратор;
- до 10 одновременных пользователей tenant АПРИ;
- объекты и история проверок;
- одна Проверка по одному объекту и одному комплекту входных данных;
- девять аналитических компетенций с выбором применимых ветвей;
- три режима: экспресс, стандарт и эксперт;
- пять верхнеуровневых экранов;
- асинхронная очередь стандартных и экспертных проверок;
- детерминированный расчётный модуль;
- опорная база и эталонные образцы;
- импорт поддерживаемых документов;
- Excel, Word и реестр нарушений;
- журнал операций;
- договорные SLA и acceptance gates.

### 5.2 Platform foundation

- tenant boundary и PostgreSQL RLS;
- tenant-scoped users, projects, documents, knowledge, analyses, exports и audit;
- две роли внутри tenant;
- immutable snapshots;
- canonical structured output;
- сменяемые LLM и embedding providers;
- два retrieval-трека с общим контрактом;
- расширяемая knowledge/parameter platform.

Platform foundation не означает, что в pilot scope входят:

- права по отдельным объектам;
- больше двух ролей;
- портфельный экран;
- tenant self-service billing;
- внешние интеграции;
- редактирование опорной базы через UI.

## 6. Одна Проверка

В соответствии с ТЗ одна Проверка:

- относится к одному объекту;
- использует один выбранный режим;
- принимает одну смету;
- принимает одно коммерческое предложение подрядчика;
- принимает одну ведомость объёмов;
- принимает один договор подряда;
- может использовать несколько внутренних LLM-вызовов и компетенций;
- создаёт новый `AnalysisRun` при изменении подтверждённых входов или параметров.

Внутренние вызовы модели и формирование нескольких выгрузок не являются отдельными Проверками.

## 7. Явно вне pilot scope

- АРПС;
- OCR PDF-сканов;
- построчный контроль КС-2/КС-3 с проектной документацией;
- визуальный контроль стройплощадки;
- специализированные экраны КС-2/КС-3, long-lead календаря, multi-contractor scoring и договорного аудита;
- права по объектам и роли сверх двух;
- портфельный режим;
- 1С, BIM и другие внешние интеграции;
- автоматическое пополнение опорной базы из закрытых документов;
- автоматические управленческие, юридические или бухгалтерские решения.

## 8. Продуктовые ограничения

Система:

- не заменяет проектную документацию, экспертизу, юриста и главного бухгалтера;
- не изменяет марку, класс и спецификацию материала;
- не прогнозирует цену продажи и спрос без входа Заказчика;
- не трактует отсутствие значения как ноль;
- не публикует число без источника или calculation trace;
- не отправляет необработанный конфиденциальный документ внешнему provider;
- не использует данные tenant для обучения provider;
- не меняет исторический результат после обновления документов, знаний или конфигурации.

## 9. Управление расширением scope

Новое требование проходит следующие шаги:

1. получает stable ID;
2. получает класс;
3. связывается с источником и literal text;
4. оценивается по влиянию на schema, расчёты, workflow, безопасность и приёмку;
5. получает decision: `include`, `defer`, `supersede`, `reject` или `needs_evidence`;
6. обновляет затронутые specs и tests/evals;
7. не считается активным до read-back и проверки ссылок.

## 10. Правила supersession

- ТЗ может отменить legacy-правило для pilot scope.
- Решение владельца может расширить platform foundation, но не должно выдаваться за требование ТЗ.
- Legacy-правило нельзя удалить без disposition.
- Известный дефект legacy становится `test_only` или negative fixture.
- Roadmap BRD не активируется автоматически.
- UI-прототип не определяет backend contract.

## 12. Gate готовности последующих specs

Компонентная спецификация допустима только если:

- связанные contract requirements имеют IDs;
- связанные legacy rules и параметры имеют dispositions;
- входные и выходные schemas определены;
- неизвестные значения и ошибки имеют явную семантику;
- acceptance evidence определено;
- out-of-scope не протекает в MVP.
